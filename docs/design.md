## Overview

census-mcp-server provides access to US Census Bureau demographic, economic, and housing data via the Census Bureau Data API (`https://api.census.gov/data`). It exposes six core dataset families — ACS 5-Year, ACS 1-Year, Population Estimates, Decennial Census, the business datasets (County Business Patterns, Economic Census, Nonemployer Statistics), and `geoinfo` (land area and internal points) — through a tool surface that abstracts the Census API's most significant usability barriers: opaque variable codes and FIPS geography requirements.

The primary design challenge is the variable system. The ACS5 2024 dataset alone has 28,475 variables with codes like `B19013_001E`. An agent can't know that `B19013_001E` is median household income without discovery tooling. The tool surface puts variable search first, makes it fast, and allows agents to confirm codes before querying.

The secondary challenge is geography. The Census API requires FIPS codes (`for=county:033&in=state:53`), but agents and users think in place names. `census_resolve_geography` bridges this, and is a mandatory first step for any agent that doesn't already have FIPS codes in hand.

Target users: agents doing demographic research, policy analysis, market sizing, geographic comparison, and any workflow that needs population, income, housing, or economic statistics for a US geography.

## Requirements

- API key required for all data queries (302 redirect without key — the API no longer supports unauthenticated data access at any rate limit)
- TIGERweb and Census Geocoder endpoints used for geography resolution — no API key required for these
- Rate limits: documented as 500 req/day without key (now moot — key required), higher with key; no hard-coded per-minute cap documented
- Read-only server — no write operations exist in the Census API
- Core datasets in scope: ACS 5-Year (`acs/acs5`), ACS 1-Year (`acs/acs1`), ACS 1-Year Supplemental Estimates (`acs/acsse`), Population Estimates (`pep/charv`), Decennial Census (`dec/pl` for 2000, 2010, and 2020; `dec/dhc`, `dec/dp`, `dec/sdhc`, `dec/ddhca`, `dec/ddhcb` for 2020), County Business Patterns (`cbp`), Economic Census (`ecnbasic`), Nonemployer Statistics (`nonemp`), Geography Information (`geoinfo`, 2020 onward)
- Latest vintages as of implementation: ACS5 2024, ACS1 2025 (with its profile, subject, comparison profile, supplemental, and selected population profile datasets), PEP 2023, CBP 2023, Economic Census 2022, Nonemployer 2024, geoinfo 2025
- ACS5 sub-tables in scope: detailed tables (`acs5`), data profiles (`acs5/profile`), subject tables (`acs5/subject`), comparison profiles (`acs5/cprofile`) — profiles cover ~80% of common queries with simpler DP-prefix codes
- ACS1 sub-tables in scope: data profiles (`acs1/profile`), subject tables (`acs1/subject`), comparison profiles (`acs1/cprofile`), and Selected Population Profiles (`acs1/spp`, filtered by `POPGROUP`; the 2008 and 2010 vintages are left out because the Census API answers them with HTTP 500)
- Out of scope: PUMS and the island-area files, which have a different shape
- Variable search operates client-side against the variables.json endpoint (28K+ variables, cached) — no Census search API exists
- Geography resolution uses TIGERweb MapServer REST API for named places, and Census Geocoder for address-to-geography lookup

## Services

| Service | Wraps | Used By |
|:--------|:------|:--------|
| `CensusApiService` | Census Data API (`api.census.gov/data`) | `census_query_data`, `census_compare_geographies`, `census_list_geographies`, `census_list_predicate_values` |
| `VariableCacheService` | Variables.json endpoints (per dataset + year), and the per-variable and groups endpoints | `census_search_variables`, `census_get_variable`, `census_list_predicate_values`, `census_query_data`, `census_compare_geographies` |
| `GeographyService` | TIGERweb MapServer REST, Census Geocoder | `census_resolve_geography` |

### Service notes

**VariableCacheService:** Variables.json files are large (28K+ entries, several MB). Cache them in-process with a TTL of 24 hours — the files change only when new vintages release. Warm on first request per (dataset, year) pair; subsequent requests are in-memory lookups. The search is a client-side keyword match against `label` and `concept` fields. Two things variables.json does not carry are fetched on first lookup and cached on the same entry, so they expire with it: an attribute column's own record from the per-variable endpoint (`…/variables/<CODE>.json`), and the per-table universes in `groups.json`. Search and the data tools fetch neither. On a `variable_not_found`, and on a search for a code that matched nothing, the same per-variable endpoint (or `groups/<id>.json` for a table ID) is asked of sibling datasets, uncached — see "A missing code names the sibling dataset that publishes it".

**GeographyService:** TIGERweb provides named-place → FIPS resolution without an API key. The geocoder resolves street addresses → census geographies (state, county, tract, block group, the county subdivision, and the incorporated place when there is one). Both are free-tier with no documented rate limits but share the service's retry/backoff wrapper. Every request one resolution makes (each level tried, respellings, the county test for an economic place, the address lookup, the namesake check) spends from one 50-second budget, the data tools' `censusCallContext`, with each attempt cut to the time left; a spent budget is `resolution_unavailable` carrying `deadlineMs`, `elapsedMs`, and `callDeadlineExceeded`, except in the namesake check, which reports the check unavailable and keeps the answer already found. A transport failure of either, once retried (an HTTP error status, a network error, a timeout), is labelled `resolution_unavailable` with its status and the step that follows, and the upstream's body never reaches the error. The geocoder answers a request it rejects with HTTP 400 and states why, as it does for an address over 100 characters; that is `address_rejected`, a validation error carrying its statement and asking for a shorter or corrected address, not an unavailable upstream.

**CensusApiService:** All data requests require the API key as `&key=...`. HTTP 302 → missing_key.html is the error when key is absent or invalid. Parse the actual JSON array response: Census returns `[["NAME","B19013_001E","state","county"], ["King County, Washington","98144","53","033"]]` — first row is headers, subsequent rows are data.

**Upstream deadlines:** `census_query_data`, `census_compare_geographies`, and `census_list_predicate_values` share one 50-second upstream-work budget per invocation (`census_resolve_geography` runs inside the same budget; see GeographyService above), including cold metadata, data, every retry and backoff, response bodies, and error-enrichment probes. `census-request.ts` carries the absolute expiry in `CensusRequestContext` while preserving the caller's signal and Context stores. Each data request also retains its 40-second ceiling and 15-second attempt ceiling, reduced to the time remaining. A stalled or unreachable upstream ends with retryable `upstream_error` or `variables_unavailable` and recovery on both output surfaces. Deterministic request errors and caller cancellation remain distinct. Optional publication/universe work may degrade inside its shorter budget, but total-call expiry cannot produce unchecked success; a sibling-hint timeout preserves an already established `variable_not_found`. Decision: per-document deadlines add together on cold calls, so only a shared invocation budget stays inside the client's timeout.

## Config

| Env Var | Required | Description |
|:--------|:---------|:------------|
| `CENSUS_API_KEY` | For keyed calls | Census Bureau API key. Request free at https://api.census.gov/data/key_signup.html. Read by `CensusApiService` before each data-endpoint request — `census_query_data`, `census_compare_geographies`, and `census_list_predicate_values` (its live route and its dictionary publication check). Optional at config parse, so the keyless tools start without it; an unset, blank, or unsubstituted key fails those calls with `missing_api_key` before any data-endpoint request, and a key the Census API rejects fails them on its first answer, unretried. |
| `CENSUS_VARIABLE_CACHE_TTL_HOURS` | No | Hours to cache variables.json per dataset+year. Defaults to 24. |
| `CENSUS_CLAMP_LIMITS` | No | Whether a `limit` above a tool's cap is served at the cap with a notice (default `true`) or rejected at the schema as `-32602` (`false`, which also advertises each cap as `maximum`). Parsed with `z.stringbool()`. See "A limit over the cap is served at the cap". |

`setup()` parses the config before any transport binds, so a malformed `CENSUS_VARIABLE_CACHE_TTL_HOURS` or `CENSUS_CLAMP_LIMITS` exits at startup with the framework's configuration banner rather than failing a tool at call time. A call with no `year` uses the newest vintage of its dataset, and the response echoes it as `year`; there is no server-wide default year.

## Implementation Order

1. Config and server setup (`CENSUS_API_KEY`, `CENSUS_CLAMP_LIMITS`)
2. `CensusApiService` — data query, response parsing (header row + data rows → labeled objects)
3. `GeographyService` — TIGERweb name resolution, Census Geocoder address resolution
4. `VariableCacheService` — fetch + cache variables.json, keyword search
5. `census_list_datasets` and `census_list_geographies` (metadata tools, no key required)
6. `census_search_variables` and `census_get_variable` (read variable cache)
7. `census_resolve_geography` (geographic resolution)
8. `census_query_data` (core data query, uses all three services)
9. `census_compare_geographies` (the same data query as `census_query_data`, one wildcard request ranked in-process)
10. `census_list_predicate_values` (enumerates the codes a `predicates` dimension accepts, from the variable cache's dataset dictionary or a live group-by query)

Each step is independently testable. Steps 5–6 can be tested without a Census API key using the public metadata endpoints.

## Tool Detail

### `census_list_datasets`

**Description:** Browse available Census datasets with their supported vintage years. Returns dataset codes, human-readable names, and descriptions. Use this as the starting point when you don't know which dataset to query — ACS5, ACS1, population estimates, and decennial census all serve different use cases.

**Input:**
- `filter?: string` — optional keyword to filter datasets by name or description

**Output:** Array of `{ dataset_id, name, description, available_years }`. `dataset_id` is the value to pass to `dataset` in other tools (e.g., `"acs/acs5"`, `"acs/acs5/profile"`).

**Errors:**
- *(none — static metadata, always succeeds)*

**Annotations:** `readOnlyHint: true`, `openWorldHint: false`

---

### `census_list_geographies`

**Description:** List the geography levels available for a given dataset and year, along with the parent geographies each level requires. Use before querying to confirm that the target geography level exists in the dataset — ACS1 omits many sub-state levels, and not all datasets support tracts or block groups.

**Input:**
- `dataset: string` — dataset code (e.g., `"acs/acs5"`, `"acs/acs1"`) — use `census_list_datasets` to discover valid values. Resolved as under "Dataset codes resolve case and two-part shorthand"; a blank value is `dataset_not_found`, worded as a missing code
- `year?: number` — vintage year (default: latest available for the dataset)

**Output:** Array of `{ geography_level, requires_parent, required_parent_levels, example }`, one entry per parent hierarchy as geography.json lists them. `geography_level` values (e.g., `"county"`, `"tract"`, `"zip code tabulation area"`) are the valid inputs to `geography_level` in `census_query_data` and `census_compare_geographies`. `totalLevels` counts distinct `geography_level` values — the count the data tools' `geography_not_supported` message gives — so a level published under several hierarchies counts once: `acs/acs5` 2024 lists 65 entries and 43 levels (county alone five times), and both surfaces say 43. The text answer names the entry count beside the level count when they differ.

**Errors:**
- `dataset_not_found` (NotFound) — unrecognized dataset code. Recovery: call `census_list_datasets` to find valid codes.
- `year_not_available` (ValidationError) — geography.json answered 404. For a year outside the dataset's `available_years`, the error matches the data tools': the message says the dataset cannot be queried for that year, the hint names the years it serves, and `data.availableYears` carries them — read from the in-process year table, no extra request. A 404 on a year the table lists is catalog drift; it keeps the plain "no geography data" message and points at `available_years` in `census_list_datasets`.
- `upstream_error` (ServiceUnavailable, retryable) — geography.json answered with an HTTP error other than a 404, or with HTML or an unparseable body. A 5xx is retried first; a rejection's hint says to change the request rather than retry it unchanged.

**Annotations:** `readOnlyHint: true`, `openWorldHint: false`

### `census_list_predicate_values`

**Description:** List the codes a Census filter dimension accepts, so a `predicates` map can be written without guessing. Answers the question left open when `census_query_data` or `census_compare_geographies` reports that a dimension was left unset. Which route a dimension takes depends on the vintage: NAICS and POPGROUP always publish a value list in the dataset dictionary; on the current vintages EMPSZES, LFO, RCPSZES, TAXSTAT, and TYPOP publish none and are enumerated against the live data endpoint instead. A dictionary value list is a classification shared across Census products rather than a record of what one dataset serves, so it is checked against the dataset's own published rows before being returned — see "Dictionary value lists are checked against published rows" below. The dictionary lists run to thousands of codes and are best narrowed with `query`.

**Input:**
- `predicate: string` — filter dimension code to enumerate (e.g., `"EMPSZES"`, `"LFO"`, `"POPGROUP"`, `"NAICS2017"`). Trimmed and uppercased before lookup, as the data tools do with `predicates` keys, and echoed in that spelling. The response notice of `census_query_data` names the dimensions a dataset declares, and `census_search_variables` finds them by keyword.
- `dataset: string` — dataset the dimension belongs to (e.g., `"cbp"`, `"nonemp"`, `"ecnbasic"`, `"dec/ddhca"`, `"dec/ddhcb"`, `"pep/charv"`, `"acs/acs1/spp"`). Use `census_list_datasets` to discover valid values. Resolved as under "Dataset codes resolve case and two-part shorthand"; a blank value is `dataset_not_found`. Dimension codes are vintage-specific, so dataset and year must match the query the values are for.
- `year?: number` — vintage year (default: latest available for the dataset)
- `query?: string` — keyword to narrow the list, matched case-insensitively against each code and label (e.g., `"software"` against `NAICS2017`, `"exempt"` against `TAXSTAT`). Omit to list from the start.
- `geography_level?: string` — live enumeration level (default: `"us"`), trimmed and lowercased. The national request uses `for=us:1`; any other level uses `for=<level>:*`. An explicit level must exist in the dataset/year's geography metadata and allow that wildcard with no concrete parents. Omitted or blank retains the national default without another metadata request. Dictionary lists keep their dataset-wide classification and national publication check; a supplied level receives a disclaimer rather than validation.
- `within_naics?: string` — industry code to scope the enumeration by, for dimensions the Census publishes per industry — `ecnbasic`'s `TAXSTAT` and `TYPOP` return only the all-establishments row until a NAICS sector is named (e.g., `"62"` for Health Care, `"42"` for Wholesale Trade). `cbp`, `ecnbasic`, and `nonemp` publish manufacturing, retail trade, and transportation and warehousing only as the ranges `"31-33"`, `"44-45"`, and `"48-49"`, so a two-digit code inside one returns nothing. Constrained at the schema to 2–8 digits or a hyphenated sector range (`"31-33"`), so a malformed code is rejected rather than silently scoping the enumeration to nothing; blank is treated as omitted. Ignored for dimensions with a published value list. Get sector codes by calling this tool on the dataset's own NAICS dimension.
- `limit?: number` — max codes to return: an integer of 1 or more (default: 50). A value over 10,000 returns 10,000 codes and the notice says so; see "A limit over the cap is served at the cap".
- `offset?: number` — matching codes to skip in code order: an integer of 0 or more (default: 0). Filtering by `query` precedes slicing. Keep predicate, dataset, year, query, `geography_level`, and `within_naics` unchanged when following `nextOffset`.

**Output:** `{ values: [{ code, label }], predicate, predicate_label, dataset, year }`. `values` is sorted by code; `code` is the value to send for this dimension in a `predicates` map, and `label` falls back to the code when the dataset publishes no label for it. Enrichment carries `totalCount` before offset/limit, `truncated` only when matches remain after this page, optional `nextOffset` only then, `source`, and an optional `notice`. Live responses also echo effective `geography_level`; dictionary responses omit that field because they do not validate level-specific publication. An offset at or past the end of an existing match set returns an empty page and a range notice, not `no_values` or a false keyword miss.

`source` names where the codes came from and whether they were checked: `"live_query"` is a wildcard group-by against the data endpoint, which returns only codes the dataset publishes; `"dataset_dictionary_verified"` is the published value map with the codes the dataset serves no rows for removed; plain `"dataset_dictionary"` is that map unchecked, and the notice says why the check did not run.

Live codes can differ by geography level, industry, and individual geography. The enumeration cache identity includes dataset, year, predicate, industry scope, measure, and effective geography level, so national and county lists never share a cached set. A code found at one level is not proof it is published at another or for every geography at that level.

`notice` explains a truncated list, a keyword that matched no published code, how many declared codes were withheld as unpublished, why a dictionary list was returned unchecked, or that the codes returned are complete only for the industry passed in `within_naics`.

**Errors:**
- `dataset_not_found` (NotFound) — unrecognized dataset code. Recovery: call `census_list_datasets` to discover valid dataset codes.
- `missing_api_key` (Unauthorized) — a dimension with no published value list is enumerated against the data endpoint, and `CENSUS_API_KEY` is unset or the Census API rejected it. Raised by the service: an unset key before any data-endpoint request, a rejected one on its first answer, never retried. Recovery: set the env var and restart. A dictionary-route call does not fail this way: its publication check is the only keyed request, so it returns the unchecked list (`source: "dataset_dictionary"`) with a notice naming `CENSUS_API_KEY` as why the check did not run — no probe when the key is unset, one unretried probe per table when it is rejected.
- `predicate_not_supported` (NotFound) — the predicate code is not a variable in this dataset and year. Recovery: call `census_search_variables` on this dataset and year for the codes it does define — dimension names are vintage-specific, so `NAICS2017` and `NAICS2022` belong to different years.
- `not_a_filter_dimension` (ValidationError) — the code is not one of the dimensions the dataset filters on, so it takes no value list. Recovery: pass a dimension the dataset filters on. The response notice of `census_query_data` names every dimension a dataset declares, and `census_get_variable` confirms what a code is.
- `geography_not_supported` (ValidationError) — an explicit live level is not in the dataset/year's metadata. Recovery: choose a level from `census_list_geographies`.
- `parent_required` (ValidationError) — the explicit live level needs concrete parents even for a wildcard. This tool accepts no parent scope, so choose a level enumerable without parents; it never falls back silently to `us`.
- `no_values` (NotFound) — the dimension returned no codes for the scope requested. Recovery names only what the call can change: when `within_naics` scoped a live enumeration and holds a two-digit code inside a published sector range (`48` for `48-49`), it names that range; when it holds any other code, drop it or try a broader industry code — a narrow leaf industry often publishes only the all-establishments row; otherwise try another year of the dataset, or confirm with `census_get_variable` that the code is the dimension meant.
- `upstream_error` (ServiceUnavailable, retryable) — Census API returned an error, was unreachable, could not provide metadata validating an explicit live level, or exceeded the shared invocation/data-request deadline. See "Upstream deadlines" under Service notes. Recovery: retry; if the error persists, the Census API may be temporarily unavailable.
- `variables_unavailable` (ServiceUnavailable, retryable) — required variables metadata could not be fetched or parsed within the call budget. Recovery: retry; if persistent, the dataset+year combination may not be available.

**Annotations:** `readOnlyHint: true`, `openWorldHint: false`

### `census_search_variables`

**Description:** Search Census variables by keyword across variable labels and concept groups, or look one up by its code. Returns variable codes with human-readable labels — use this to go from a concept like "median household income" to the variable code `B19013_001E` needed for data queries. A query that is one variable or table code returns that variable or the table's variables ahead of any keyword match. Returns both estimate (`E` suffix) and margin-of-error (`M` suffix) codes so you can request both.

**Input:**
- `query: string` — keywords to search (e.g., "median household income", "poverty", "bachelor's degree"), or one variable or table code (`B19013_001E`, `B19013`), matched by the rule under "Variable search is client-side, not a Census API feature"
- `dataset?: string` — dataset to search within (default: `"acs/acs5"`), resolved as under "Dataset codes resolve case and two-part shorthand"
- `year?: number` — vintage year (default: latest available for the resolved dataset, so `"pl"` searches `dec/pl` 2020)
- `limit?: number` — max results to return: an integer of 1 or more (default: 20). A value over 3,000 returns 3,000 variables and the notice says so; see "A limit over the cap is served at the cap".
- `offset?: number` — matching variables to skip in the complete search order: an integer of 0 or more (default: 0). Keep query, dataset, year, and limit unchanged when following `nextOffset`; code-tier matches remain ahead of keyword matches across page boundaries.

**Output:** Array of `{ variable_code, label, concept?, predicate_type }` in search order. `variable_code` is the value to pass to `census_query_data`. `concept` is absent for a column shared across tables (`GEO_ID`, the `ecnbasic` measures), whose published concept joins every table's, and for a column the dataset publishes no concept for (the ACS `STATE` column). Enrichment carries `totalMatches` before offset/limit, `truncated` when matches remain after this page, and optional `nextOffset` only then. The count is the code tier plus variables containing every query word, or, when none does and no code matched, those containing the most. Notices preserve partial-word guidance alongside continuation, name the last code when a table continues, and distinguish a final or past-end page from a genuine no-match. A code-shaped query that matched nothing whole instead points to `census_get_variable` for a listed attribute column (`B19013_001EA`), a confirmed sibling dataset (`S1701` in `acs/acs5` names `acs/acs5/subject`), or checking the code and vintage when no sibling was confirmed.

**Errors:**
- `dataset_not_found` (NotFound) — unrecognized dataset code. Recovery: call `census_list_datasets` for valid codes.
- `year_not_available` (ValidationError) — the dataset cannot be queried for the requested vintage. Raised from `DATASET_AVAILABLE_YEARS` before any request. Recovery: retry with a year the error names.
- `variables_unavailable` (ServiceUnavailable, retryable) — variables.json could not be fetched or parsed, including exhausted network or body-read failures. Recovery: retry; if persistent, the dataset+year combination may not be available.
- `upstream_error` (ServiceUnavailable, retryable) — variables.json answered with an HTTP error. A 5xx is retried first; a rejection's hint says to change the request rather than retry it unchanged.

**Annotations:** `readOnlyHint: true`, `openWorldHint: false`

### `census_get_variable`

**Description:** Fetch full metadata for one or more variable codes — label, concept group, predicateType, and the table's universe — including the annotation and flag columns the data tools accept (`B19013_001EA`, `EMP_F`), each with the column it belongs to. Use to confirm a variable code before building a query, or to look up what a known code means.

**Input:**
- `variables: string[]` — one or more variable codes (e.g., `["B19013_001E", "B19013_001M"]`), trimmed and resolved to the dataset's own spelling by `VariableCacheService.resolveSpellings`, the resolver the data tools share (see "Codes are sent in the dataset's spelling"). The per-variable endpoint 404s a lowercase code, so this runs before the attribute-column lookup. The response echoes the dataset's spelling.
- `dataset?: string` — dataset the variables belong to (default: `"acs/acs5"`), resolved as under "Dataset codes resolve case and two-part shorthand"
- `year?: number` — vintage year (default: latest available)

**Output:** Array of `{ variable_code, label, concept?, predicate_type, universe?, attribute_of?, attribute_type? }` in the same order as the input array. Includes `estimate_code` and `moe_code` sibling references where applicable, so the agent can request both without a separate search. An ACS margin-of-error code also carries `attribute_of` (its estimate) and `attribute_type: "MARGIN_OF_ERROR"`. The enrichment block carries a `notice` when the universe lookup failed (see `universe` below).

- `concept` is absent for a column shared across tables, and for one the dataset publishes no concept for — the same rule search applies.
- `universe` is read from the dataset's `groups.json`, published under the key `"universe "` (with a trailing space), and joined on the variable's single-table `group`. It is absent when the table publishes none — every table on the ACS subject, profile, comparison profile, and selected population profile datasets, `dec/dp`, `cbp`, `ecnbasic`, `nonemp`, `pep/charv`, and `geoinfo`, and on every ACS and `dec/pl` vintage before 2020 (the `acs/acs1` and `acs/acsse` universes start in 2021) — and for a column that belongs to no single table. A probe of every registered dataset and vintage found `groups.json` published for all of them, at most 422 KB (`acs/acs1` 2024), fetched once per dataset and year. A `groups.json` 404 means the dataset publishes none, and `universe` is omitted with nothing said. Any other failure — a 5xx, a network error, a timeout, an HTML or unparseable body, a body with no `groups` list — still returns the variables without `universe`, once retries are spent or 20 seconds have passed, plus a `notice` naming the single-table codes that lost it and saying to retry, so the absence cannot be read as "this table publishes no universe". The failure is not cached, so the next call fetches `groups.json` again, and a caller's cancellation stays a `RequestCancelled` error rather than a result with a notice. Decision: the variable record comes from `variables.json`, which answered; failing the whole call over one optional field threw away the label, concept, type, and sibling codes, and the notice answers the objection that a silently omitted field claims the table has no universe. Decision: the 20-second bound covers every attempt and backoff, since four 30-second attempt timeouts held a stalled `groups.json` call for 139 s, past the 60-second request timeout MCP SDK clients apply by default; four fast failures and their backoff still fit inside it.
- `attribute_of` and `attribute_type` are set on annotation and flag columns. variables.json lists these only inside another entry's `attributes` string, so the cache indexes every name listed there. A code found only in that index is fetched from the per-variable endpoint, which publishes the column's label, `"attribute of"`, and `"attribute type"`. `attribute_type` is normalized to upper-snake case (trimmed, uppercased, whitespace to `_`): current vintages publish `ANNOTATION`, `FLAG`, `GROUPING`, `LABEL`, and `STATISTICAL_SIGNIFICANCE`, but `acs/acs5` and its profile and subject tables through 2010, the 1-year ACS datasets through 2011, and `dec/pl` 2010 write `Annotation`, `Margin of Error`, `Label`, `Statistical Significance`, and `Errata`, and relayed as published one call could mix `Annotation` with a margin of error's `MARGIN_OF_ERROR`. The rule is mechanical rather than a lookup table, so a kind a later vintage introduces passes through normalized; the field stays a string. `attribute_of` is relayed as published, so `NAICS2017_F` on `cbp` is an attribute of `NAICS2017_LABEL`, not of the `NAICS2017` entry that lists it. A code in neither the variable map nor the index is `variable_not_found`, with no request sent. Attribute columns stay out of search results and the predicate check.

**Errors:**
- `variable_not_found` (NotFound) — one or more codes not found in the dataset. Response includes which codes failed. Its recovery names the sibling dataset that publishes a missing code where one is confirmed, and suggests calling `census_search_variables` for the rest; see "A missing code names the sibling dataset that publishes it".
- `dataset_not_found` (NotFound) — unrecognized dataset code.
- `year_not_available` (ValidationError) — the dataset cannot be queried for the requested vintage. Raised from `DATASET_AVAILABLE_YEARS` before any request.
- `variables_unavailable` (ServiceUnavailable, retryable) — variables.json could not be fetched or parsed, or an attribute column's per-variable record could not be fetched. An optional `groups.json` failure ordinarily degrades without failing the lookup; see `universe`.
- `upstream_error` (ServiceUnavailable, retryable) — variables.json answered with an HTTP error. A 5xx is retried first; a rejection's hint says to change the request rather than retry it unchanged.

**Annotations:** `readOnlyHint: true`, `openWorldHint: false`

### `census_resolve_geography`

**Description:** Resolve a place name or ZIP code to Census FIPS identifiers. Converts "King County, WA", "Seattle, WA", "Seattle-Tacoma-Bellevue, WA", or "98109" to the codes required by `census_query_data` and `census_compare_geographies`. Also accepts street addresses, which resolve to their tract with the block group, incorporated place, and county subdivision alongside. Returns the FIPS values directly ready to pass to other tools, and a `geography_type` that is itself the `geography_level` to query at.

**Input:**
- `name: string` — place name (e.g., "King County, WA", "Seattle, WA", "Chatham County, Georgia"), 5-digit ZIP or ZIP+4, or street address (e.g., "1600 Pennsylvania Ave NW, Washington, DC 20500")
- `geography_type?: string` — geography level to resolve to: `"state"`, `"county"`, `"place"`, `"tract"`, `"metropolitan statistical area/micropolitan statistical area"`, `"combined statistical area"`, `"consolidated city"`, `"zip code tabulation area"`, `"economic place"`, `"county subdivision"` (default: auto-detect from name). Each value is the level's own Census API name, so it feeds `census_query_data`'s `geography_level` unchanged.
- `county_fips?: string` — 1 to 3 digits, zero-padded to 3, restricting resolution to a single county. Only `county`, `county subdivision`, and `tract` sit within a county, so it also narrows auto-detection to those three levels rather than riding along on a layer that cannot apply it

**State suffix:** split once, before any query. After a comma, the whole final segment must name a state — a full name or territory alias matched exactly and case-insensitively ("Chatham County, Georgia"; "McDowell County, West Virginia" never reads as Virginia), or two-letter abbreviations in either case, alone or as a hyphenated list ("NE-IA"), which scopes by its first state. Without a comma only an uppercase abbreviation splits, since a trailing state word cannot be told apart from a place name ending in one.

**Auto-detection:** a bare 5-digit ZIP or ZIP+4 resolves at the ZCTA layer; a two-letter abbreviation or a spelled-out state name (matched against the whole input, so "West Virginia University" is not a state) at the state layer; the word `"County"` or `"Parish"` at the county layer; the word `"Borough"` at the county layer, then the place layer (an Alaska borough is a county-equivalent, a PA or NJ borough is a place); the word `"Tract"` at the tract layer. Keywords match whole words, so "Marlborough, MA" and "Parishville, NY" are tried as places. Everything else is tried at the place level — incorporated places (TIGERweb `Places_CouSub_ConCity_SubMCD` layer 4) and census-designated places (layer 5) together, since the Census `place` level is both — and falls back to county when the place level has no row, then, for a state suffix naming one of the twelve states below, to county subdivision. It also falls through when the place level's rows only contain the name, and the county level has one named exactly that: "King, WA" finds Kingston CDP by `LIKE`, but King County is the exact name. A place row that only contains the name is still the answer when no later level has an exact one ("Winston, NC" → Winston-Salem). Matching ignores case (`UPPER(NAME) LIKE`, since TIGERweb's `LIKE` is case-sensitive). Rows whose name is exactly the queried term win over longer `LIKE` matches, so "Kansas City, MO" resolves to Kansas City rather than North Kansas City; a row whose `BASENAME` is the term outranks one whose full `NAME` is, so "Jersey City" is not tied with the `NAME` "Jersey city" of Jersey, GA. Whatever survives that filter must be a single row to resolve — two or more are distinct real geographies (bare "Boston" matches towns in IN, GA, and MA), so they come back as `ambiguous_name` rather than a coin flip. `"New York"` is a standing ambiguity — it is both the state name and the Census place name for New York City, so auto-detection resolves the state and the city needs `geography_type: "place"`. The three statistical/consolidated levels and `economic place` are never auto-detected — their names overlap city names — so each needs an explicit `geography_type`. A state suffix scopes them too, but through the row names rather than a WHERE clause: the CBSA and CSA layers carry no `STATE` field, and their names end in the hyphenated list of states the area spans, so "Kansas City, MO" and "Kansas City, KS" both reach the MO-KS metro area. On those layers the exact-name comparison drops that state list from `BASENAME`, so "Bend, OR" is the Bend metro area rather than a tie with Coos Bay-North Bend.

**Retries:** every level in the chain is queried for the name as given first, so a real name on a later level beats a respelling on an earlier one. Only when none has a row are respellings tried, level by level, each through the same exact-name preference, cross-level ranking, and `ambiguous_name` handling, with a level's first respelling that finds rows standing for that level: the Saint token in TIGERweb's forms (`Saint`/`St` → `St.`, `Sainte`/`Ste` → `Ste.`, and `St.` → `Saint` for "Saint Jo"); then the name with every letter that carries an accent somewhere in the vocabulary (`a i n o u`) wildcarded, keeping only rows whose accent-folded name contains the term ("Dona Ana County, NM" → Doña Ana County); then, on the CBSA and CSA levels, the leading city alone (the text before the first hyphen). OMB renames an area by its trailing cities, and every CBSA renamed between the 2020 and 2023 delineations kept its leading city, so "Denver-Aurora-Lakewood, CO" resolves to Denver-Aurora-Centennial (`19740`), and a merged CSA resolves to the area now containing the city ("Kerrville-Fredericksburg, TX" → `484`). The state, tract, consolidated-city, and ZCTA vocabularies carry neither Saint abbreviations nor accents, so they are never retried. A no-match costs about twice the requests it did in 0.4.0, and a short name made only of accent-bearing letters wildcards to a pattern matching nearly every name on the layer: a bare "Uaio" downloads several megabytes (1.8 MB from the incorporated-places layer alone) and takes about 3 s to reach `no_match`. The layers' 100,000-row `maxRecordCount` exceeds every layer's size, so no match is cut off.

**Census-designated places:** a CDP resolves at the place level with `census_designated_place: true`, and the Data API takes its code at `place` like any other ("Bethesda, MD" → `07125`). A CDP is a statistical area, so it answers a name only when no incorporated place or county has that exact name: among a level's exact rows an incorporated place outranks a same-named CDP ("Paradise, CA" is Paradise town, not the Paradise CDP in Mono County; bare "Tacoma" is still Tacoma, WA), and a place level whose exact rows are all CDPs yields to an exact county, the way a row that only contains the name does ("Arlington, VA" is Arlington County, "San Juan, PR" San Juan Municipio). An exact CDP still outranks a county that only contains the name ("Chester, VA" is Chester CDP, not Chesterfield County). The CDP stays reachable by its full name ("Arlington CDP, VA") or with `geography_type: "place"`. The same ranking applies to respellings ("Dona Ana, NM" → Doña Ana County). A state suffix scopes both place layers, so a CDP in another state never displaces a state-scoped city. Address resolution still reports only incorporated places, since the geocoder layers requested carry no CDPs.

**County subdivisions:** `geography_type: "county subdivision"` resolves in every state, against TIGERweb `Places_CouSub_ConCity_SubMCD` layer 1, and returns `state_fips`, `county_fips`, and the 5-digit code as both `fips_summary` and `county_subdivision_fips`. The "County subdivisions not defined" placeholder row of a county with none is never a match. A trailing "Township" also asks for the "<name> charter township" form, which the substring of a Michigan charter township's name does not contain ("Clinton Township, MI" reaches Clinton charter township), and an exact-name preference reads the two forms as the same name. Auto-detection reaches the level only for a state suffix naming CT, ME, MA, MI, MN, NH, NJ, NY, PA, RI, VT, or WI, the twelve states whose towns and townships are general-purpose local governments that can perform the same functions as incorporated places (Census geography glossary, "County Subdivision"), and tries it after place and county. An exact subdivision then outranks a CDP named exactly the input and a place that only contains it ("Cherry Hill, NJ" is Cherry Hill township `12280`, not Cherry Hill Mall CDP), and an exact county still answers first ("Plymouth, MA" is Plymouth County). Elsewhere a subdivision is a census county division or a township without a place's powers — nonfunctioning, or a government such as an Ohio or Illinois township (TIGERweb marks 1,308 Ohio and 1,411 Illinois subdivisions `FUNCSTAT` `A`) — that would displace a closer answer ("Winston, NC" is Winston-Salem, not Winston township), so it needs the explicit type. Two answers carry a check for a same-named subdivision with its own government (`FUNCSTAT` `A`) within the caller's state and county scope: a county auto-detected through that chain, and a CDP resolved at `geography_type: "place"` in those states. When one matches, the `notice` names it with its county and code; when TIGERweb cannot answer the check, the notice says it did not run rather than failing the answer already found. A borough is skipped, since it has its own notice and is no government. Names repeat across a state's counties, so candidates of an `ambiguous_name` are separated by county and `county_fips` is the input that picks one.

**New York City boroughs:** each borough is coextensive with one county (TIGERweb holds exactly one county subdivision, the borough, in each of the five), and three are published under a different county name. When the state suffix is New York, the county level queries a borough name as its county's name — Brooklyn → Kings (`047`), Manhattan → New York (`061`), Staten Island → Richmond (`085`), Bronx or The Bronx → Bronx (`005`), Queens → Queens (`081`), each also with a trailing "borough" ("Queens borough, NY", the county subdivision's own name). The substitution is that level's query term, not a retry, so a place row that only contains the borough name never outranks the county, and a name already the county's ("Queens, NY", "Bronx, NY") sends the same requests as any other name. A result reached through it carries a `notice` naming the borough. The place level keeps the name as given — "Manhattan" read as "New York" there would answer with New York city (`51000`) — so "Brooklyn, NY" at `geography_type: "place"` is `no_match`, and its hint names Kings County. A borough is no place, so on the place and economic place levels a row that only contains a borough name never answers it, from the as-given query or any respelling: "Bronx, NY" at `place` is `no_match` naming Bronx County rather than Bronxville village (`08532`), which "Bronxville, NY" still reaches, and "Queens, NY" at `economic place` is `no_match` naming Queens County rather than Queensbury town. The hint also names "New York, NY" for the city as a whole at `place`, or at `economic place` when that level missed, since `ecnbasic` keys the city by its 8-digit economic place code. A place named exactly the borough name would still answer. Without a New York suffix nothing is substituted: bare "Brooklyn" stays `ambiguous_name` among places, and "Manhattan, KS" is Manhattan city.

**Connecticut counties before 2022:** current TIGERweb holds only Connecticut's nine planning regions (`110`–`190`), while every dataset vintage through 2021, the 2020 Census included, publishes the eight counties they replaced. With a Connecticut suffix, the county level answers those eight names from a fixed table with no TIGERweb request: Fairfield `001`, Hartford `003`, Litchfield `005`, Middlesex `007`, New Haven `009`, New London `011`, Tolland `013`, Windham `015`. The table answers a name that says "County" ("Fairfield County, CT", any case, or the full state name) or a lookup at `geography_type: "county"`; a `county_fips` naming another code is `no_match`. A bare "Fairfield, CT" in an auto-detected chain is left to the current geographies and resolves to Fairfield town, since the table would otherwise end the chain on county `001` before the subdivision level. The result carries a `notice` that the code is the pre-2022 county, published through 2021, and that vintages from 2022 publish the planning regions. A planning region by its own name ("Western Connecticut Planning Region, CT" is `190`) resolves through TIGERweb with no notice, and without a Connecticut suffix nothing changes ("Fairfield County, OH" is Ohio county `045`). A Connecticut county subdivision carries its planning-region county, the one vintages from 2022 publish it under, so a town's `county_fips` is wrong for a vintage through 2021.

**Economic places:** `ecnbasic` 2022 publishes `economic place`, whose 8-digit code is the 3-digit county the place lies in (`000` when it spans counties) followed by its 5-digit place code — Seattle is `03363000`, Auburn, WA (King and Pierce) `00003180`. The name resolves against TIGERweb `Econ/EconPlaces` 2022 layers 2 (incorporated places and minor civil divisions), 3 (CDPs), and 4 (balance of county), which list every economic place whether or not it has published data; the Data API itself cannot list them without a sector. Those layers carry no county, so the prefix comes from the 2022 boundaries (`tigerWMS_ACS2022`): a balance of county is coded `98` + its county; an incorporated place or CDP polygon is sent to the 2022 counties layer as a DE-9IM interior test (`T********`), so a county it only borders does not count; and a layer-2 place with no place polygon is a minor civil division, whose county subdivision row names its one county (Edison township, NJ → `02320230`). Both sides of the test are full-resolution polygons from that one vintage, so a place and its county share their edges exactly; a generalized polygon does not, and produces slivers (Houston picked up Brazoria County at a `maxAllowableOffset` of 0.0005). A place too small to be an economic place (Krupp, WA) is `no_match`, and the hint names the county's "Balance of … County" that holds it. `ambiguous_name` candidates carry the 5-digit place code rather than a guessed prefix. The 2017 and 2012 vintages publish `place` instead, keyed by the plain 5-digit code `place_fips` already carries.

**ZIP codes:** a ZIP resolves on the 2020 Census ZCTA layer by exact `GEOID`, to `geography_type: "zip code tabulation area"` with no `state_fips` — the layer has none, and a ZCTA can straddle a state line. A resolved ZCTA is queried with no parent on `acs/acs5` and `acs/acs5/profile` from 2020 and `acs/acs5/subject` from 2019; the 2011–2019 ACS 5-year vintages require `in=state`, which the caller supplies from the state's own name. A ZCTA is never `cbp`'s `zip code` level: that level takes the ZIP itself and needs no resolution, and many ZIPs with `cbp` data (PO-box ZIPs such as `98111`) have no ZCTA.

**Output:** `{ name, geography_type, state_fips?, county_fips?, county_subdivision_fips?, tract_fips?, block_group_fips?, place_fips?, census_designated_place?, fips_summary }`. `fips_summary` is a pre-formatted string ready to use as `geography_fips` in `census_query_data` (e.g., `"033"` for a county, with `state_fips: "53"` as the parent; `"42660"` for the Seattle-Tacoma-Bellevue metro area, with no parent at all). A street address resolves to its tract — `geography_type` and `fips_summary` stay at the tract — and also carries `block_group_fips` from the geocoder's `2020 Census Blocks` layer, `county_subdivision_fips` from its `County Subdivisions` layer, and `place_fips` from its `Incorporated Places` layer, the request asking for layers 8, 12, 22, and 28: `400 Broad St, Seattle, WA 98109` → tract `007101`, block group `2`, county subdivision `92928`, place `63000`. An address outside every incorporated place has no `place_fips`. The county subdivision goes to `census_query_data` at `county subdivision` as `geography_fips`, with the address's `state_fips` as `parent_fips` and `county_fips`. The block group goes to `census_query_data` as `geography_fips` at `block group`, with `tract_fips` set to the tract. Every state-hierarchy level carries `state_fips` — the parent geography most sub-state queries require. A metropolitan/micropolitan or combined statistical area omits it: those levels can span several states and take no `parent_fips`, so reporting the `"00"` a missing field would pad to would be a fabricated parent. A ZCTA omits it too, since its layer carries no state. The enrichment block carries an optional `notice`, present when a New York City borough resolved to its county under the county's name (`"Brooklyn" is the New York City borough coextensive with Kings County.`), when a county or CDP answer has a same-named county subdivision with its own government (or the check could not run), when the answer is a Connecticut county from before 2022, and on every result that carries `tract_fips`. The tract notice says it is a 2020 tract, published from ACS 5-year 2020 and the 2020 Census files, where earlier vintages publish 2010 tracts (2000 tracts on `acs/acs5` 2009 and `dec/pl` 2000) and the code can be missing; for Connecticut it adds that the tract sits under its planning region, vintages through 2021 publish the same tract code under one of the eight earlier counties, and `census_query_data` at the tract level with `geography_fips "*"`, `county_fips "*"`, and `parent_fips "09"` lists each under its county there. Several notes join into the one string, in that order.

**Errors:**
- `no_match` (NotFound) — no layer in the chain had a row for the name or any respelling. A New York City borough missed at the place level, or ruled out by `county_fips`, gets a hint naming its county and county code. The message is built from the split name, so it names the place and state apart and never appends a second state to a name that already carries one; the hint carries only the next steps, so neither repeats the other. When the input carried no state, the hint asks for a state abbreviation, an explicit `geography_type` naming a level not yet tried, or a full street address. A statistical-area miss instead suggests naming the area by a single city it contains. A ZIP miss's message says the ZIP was checked only as a ZCTA, and its hint that `cbp` takes the ZIP itself as `geography_fips` at `zip code`. An economic-place miss says which places qualify and points at the county's balance. An economic place whose 2022 boundary is missing is also `no_match`, since a guessed county prefix would name a different code; its message gives the place code and its hint the `"*"` query to find it in. An address the geocoder cannot match asks for a ZIP only when the address carries none.
- `ambiguous_name` (ValidationError) — more than one geography matched. `candidates[]` carries `{ name, geographyType, stateFips, stateAbbr, countyFips?, tractFips? }` and the recovery hint lists them ready to re-query. Only the state layer returns `STUSAB`, so the abbreviation is derived by reversing the state FIPS table. Tract and county subdivision candidates repeat the same name within a state ("Springfield, PA" matches townships in several counties), so they are separated by county and the hint sends the caller back to this tool with `county_fips` set, which picks one unless two share a county (Maine's Rangeley town and Rangeley plantation, both county 007); then the hint adds the full name as listed, which tells them apart. Statistical-area candidates carry no state at all, so the code each resolves to is what makes them actionable. Economic-place candidates carry `placeFips` instead of `fipsSummary`: the county prefix takes a spatial lookup per place, so the hint sends the caller back with the candidate's name.
- `county_scope_unsupported` (ValidationError) — `county_fips` was paired with a street address, or with a level that does not sit within a county, whether set explicitly or auto-detected. Thrown before any network call. Recovery: drop `county_fips`, or set `geography_type` to `"county"`, `"county subdivision"`, or `"tract"`.
- `address_rejected` (ValidationError) — the Census Geocoder answered HTTP 400 for the street address as sent (one over 100 characters, for one); the message carries the geocoder's own statement of why, also in `upstreamMessage`. Not retried. Recovery: a shorter or corrected address, or resolve the city or county by name instead.
- `resolution_unavailable` (ServiceUnavailable, retryable) — TIGERweb or the Census Geocoder failed with an HTTP error, could not be reached, or did not answer in time on every attempt or within the call's 50-second upstream budget, or answered with a page or an error in place of data. A spent budget carries `deadlineMs`, `elapsedMs`, and `callDeadlineExceeded`. Recovery: retry the request; if it keeps failing, the Census geography service is temporarily unavailable. An HTTP status that is a refusal rather than a transient failure is not retryable, and its hint says to resolve the geography by another name or level, or to pass FIPS codes already in hand to the data tools; the code stays ServiceUnavailable whatever the status, so a TIGERweb 404 never reads as `no_match`'s NotFound.

**Annotations:** `readOnlyHint: true`, `openWorldHint: false`

### `census_query_data`

**Description:** Query a Census dataset for one or more variables at one geography, a comma-separated list of geographies at the same level, or every geography at a level. Requires FIPS codes for the target geography — call `census_resolve_geography` first to convert place names. Returns estimates with margin-of-error values alongside each, and each variable's label once in `variable_labels`. ACS sentinel values in the data (negative values like -666666666) are surfaced with the meaning the Census publishes rather than passed through as raw numbers, and a value a business dataset withheld — stored as `0` beside a flag — is reported as withheld. See "ACS sentinel values resolve by number" and "Business-dataset flags" below.

**Input:**
- `variables?: string[]` — variable codes to retrieve (e.g., `["B19013_001E", "B19013_001M"]`); optional when `group` is set, and one of the two is required. Matched regardless of case and sent in the dataset's own spelling, which keys each row; see "Codes are sent in the dataset's spelling" below. At most 49 per call, and fewer where the server adds label or record columns — see "The 50-column limit counts every column sent" below. Use `census_search_variables` to find codes. Always include the MOE counterpart (swap `E` → `M` suffix) to get margin-of-error alongside each estimate. An entry written `group(<ID>)` reads as `group`.
- `group?: string` — one table ID (e.g., `"B01001"`) whose every column to retrieve in one call, beside or in place of `variables`. See "A table comes back whole through `group`" below.
- `geography_level: string` — level of the target geography (e.g., `"county"`, `"tract"`, `"state"`, `"zip code tabulation area"`). Use `census_list_geographies` to see valid values for the dataset.
- `geography_fips: string` — FIPS code for the target geography at the requested level (e.g., `"033"` for a county, `"*"` for every geography at that level within the parent, returned `limit` rows at a time). Use `census_resolve_geography` to obtain this value. A comma-separated list (`"06,53"`, or `"033,061"` with `parent_fips: "53"`) names several geographies at the level; see "A geography_fips list is several geographies" below. At county, place, school district (unified), economic place, congressional district, county subdivision, tract, block group, and block, a member that is exactly the level's GEOID width and all digits is a full GEOID, as `geography_geoid` returns it, and is read as its parents plus the level code (`"53053"` is county `"053"` under state `"53"`); see "Full GEOIDs are read in the tool" below.
- `parent_fips?: string` — FIPS of the parent geography when the level requires one (e.g., state FIPS `"53"` when querying counties within WA). Required for sub-state levels, unless every `geography_fips` member is a full GEOID naming the same state. `census_resolve_geography` returns this as `state_fips`. `"*"` spans every state only where the level's `geography.json` entry lists `state` under `wildcard` (county and place on every served dataset-year; never tract, block group, or county subdivision) — anywhere else the Census API answers `400` "wildcard not allowed for 'state' in geography hierarchy", so the check refuses it as `parent_required` first.
- `county_fips?: string` — county FIPS when querying county subdivisions, tracts, or block groups inside one county (e.g., `"033"` for King County), alongside `parent_fips`; optional when every `geography_fips` member is a full GEOID naming the same county. `census_resolve_geography` returns this as `county_fips`. `"*"` spans every county only where the entry lists `county` under `wildcard` (tract, block group, and most county subdivision entries), and never under a `tract_fips`.
- `tract_fips?: string` — tract code scoping the query to one tract (e.g., `"007101"`), appended to `in=` after the county. Exactly 6 digits, never padded (a person writes Tract 71.01 as "7101" or "71", and "71" would pad to a different tract) and never `"*"` (upstream answers `tract:*` under a concrete block group with a `400`, and under a wildcard it adds nothing). A blank value is omitted. It needs a concrete `county_fips`, since a tract code is unique only inside its county and upstream rejects a tract without one. A block group or block GEOID in `geography_fips` carries its tract, so it supplies this input. `dec/pl` 2000 lists a whole-number tract (a code ending in 00) by its first 4 digits, so there a 6-digit `tract_fips` ending in 00 is sent in that form (`"007100"` as `"0071"`) and the notice says so; a 4-digit `tract_fips` is not accepted. The dataset's `geography.json` decides which levels take it: `block group` on `acs/acs5`, `block group` and `block` on `dec/pl`. `census_resolve_geography` returns it as `tract_fips`.
- `predicates?: Record<string, string>` — dataset-specific filter values keyed by variable code (e.g., `{ "NAICS2017": "5112" }`), appended to the request URL as extra query parameters. Keys are uppercased and a blank value is omitted; `"*"` returns one row per category, labelled in `record`. See "Predicate filtering" below.
- `dataset?: string` — dataset to query (default: `"acs/acs5"`). Use `census_list_datasets` for valid values. Resolved as under "Dataset codes resolve case and two-part shorthand".
- `year?: number` — vintage year (default: latest available for the dataset)
- `limit?: number` — most rows to return: an integer of 1 or more (default: 50). A value over 500 returns 500 rows and the notice says so; see "A limit over the cap is served at the cap". Each row counts, so a `pep/charv` geography's April and July records, or the per-category rows of a `"*"` predicate, take one each.
- `offset?: number` — rows to skip before returning up to `limit`: an integer of 0 or more (default: 0). See "Wildcard results are capped and paged" below.

**Output:** `variable_labels`, a map of variable code to label, and an array of result rows, each with `{ geography_name, geography_fips, geography_geoid, variables: { [code]: { estimate, moe?, suppressed, suppression_reason?, open_ended?, flag?, value? } } }`. Suppressed values include the `suppression_reason` the Census publishes (e.g., "Estimate not computable: too few sample observations …") rather than the raw negative sentinel. `open_ended` marks an ACS median at an open-ended interval's boundary, and `flag` carries a business dataset's `{ code, meaning }`. `value` carries the text of a cell that does not hold a number, which is what makes a null `estimate` readable — see "A null estimate resolves three ways" below. A wildcard or comma-separated list is paged in GEOID/record order. Enrichment carries `totalRows` returned, `totalCount` before offset/limit, `truncated` only when rows remain after the current page, and optional `nextOffset` only then. Notices independently explain the returned range, final/past-end pages, and listed codes with no matched row; an off-page match is never reported absent.

Each row carries two identifiers because they serve different purposes. `geography_fips` is the bare code at the queried level (`"033"`) — what the Census API `for=` clause takes, so it round-trips back into this tool's own `geography_fips` input alongside the same parents. `geography_geoid` concatenates the level with its parents (`"53033"` for a county, `"53033000101"` for a tract) and is nationally unique, so it is the identifier that works when geographies span states — notably in `census_compare_geographies`'s `geographies` filter. It also goes back into this tool as `geography_fips` at the levels that read a full GEOID.

`variable_labels` names each requested code the dataset labels once for the response, in the order the rows key the variables, instead of repeating the label on every row of every page. It is built from the request, so every page of one query, a page past the end included, carries the same map. A code the dictionary gives no label, an annotation or flag column such as `B19013_001EA` or `EMP_F`, has no entry. `content[]` renders the map as one "Variable labels" legend ahead of the rows, each label escaped so a CommonMark parse reads it back exactly, and prints each number with every digit `structuredContent` carries and en-US thousands separators on the integer part, whatever the host locale.

A row also carries `applied_filters` (the label of the default the API applied to each filter dimension the query left unset) and, on a dataset that publishes more than one record per geography, `record` — keyed by the column that separates the records, each value carrying a `code` and a `label`, e.g. `{ "MONTH": { "code": "7", "label": "July" } }`. The code is what pins the record when passed back in `predicates`. Both are absent when they do not apply. See "Several records per geography are labelled, not collapsed" below.

**Errors:**
- `variables_or_group_required` (ValidationError) — neither `variables` nor `group` names anything: both omitted, or every value blank ("At least one variable code or a table in group is required."). Raised before any request.
- `multiple_groups` (ValidationError) — `group` and the `group(<ID>)` entries of `variables` name more than one table; the Census API returns one table per request. Raised before any request.
- `group_not_supported` (ValidationError) — `group` was set on `cbp`, `ecnbasic`, `nonemp`, `pep/charv`, `dec/ddhca`, `dec/ddhcb`, or `acs/acs1/spp`, whose tables carry the filter or record dimensions that turn the API's default into one row per category. Raised before any request; recovery lists the codes in `variables` with `predicates`.
- `missing_api_key` (Unauthorized) — `CENSUS_API_KEY` not configured or invalid. An unset key fails before any data-endpoint request; a rejected one fails on the Census API's first answer, unretried. Recovery: set the env var and restart.
- `year_not_available` (ValidationError) — the dataset cannot be queried for the requested vintage. Raised from `DATASET_AVAILABLE_YEARS` before the handler's first request, so a wrong year costs no round trip. The recovery hint names the years that do work, contiguous runs collapsed (`2005-2019, 2021-2025`); the message states only the refused year.
- `variables_unavailable` (ServiceUnavailable, retryable) — required variable metadata could not be fetched or parsed within the shared call budget, surfaced through the predicate check. Recovery: retry.
- `variable_not_found` (NotFound) — the Census API rejected a variable code as unknown for the dataset+year. Mapped from its `400` `error: unknown variable '<code>'` body, which names the first unknown code only; see "Upstream error bodies are read" below. It also covers a `group` table the dataset does not publish, checked against the cached `variables.json` before the data request. Recovery: the sibling dataset that publishes the code when one is confirmed (see "A missing code names the sibling dataset that publishes it"), otherwise `census_search_variables` or `census_get_variable` to confirm codes.
- `geography_not_supported` (ValidationError) — the requested geography level does not exist in this dataset and year. Thrown before the data query, from the dataset's own geography metadata; the error carries the levels the dataset does have. Recovery: call `census_list_geographies` to see supported levels.
- `parent_required` (ValidationError) — the geography level requires a parent the request did not supply (e.g., tract requires a state, block group a state and a county). Thrown before the data query, from the same metadata; the error names the missing parents and the recovery hint names the input to add. A `*` target relaxes the innermost required parent, which is why a nationwide `county` query needs no `parent_fips` while a tract query does. A single block group missing its tract gets a hint naming `tract_fips`, and a `tract_fips` whose `county_fips` is omitted or `"*"` is `parent_required` naming `county_fips`. A `"*"` `parent_fips` or `county_fips` counts as that parent only where the entry lists it under `wildcard`; anywhere else it is a parent still to name, the message says `"*"` does not stand in for it, and the hint asks for one concrete code in its place (a `"*"` state on `tract`, which the API would answer with a `400`). A list of full GEOIDs that spans several states or counties gets a hint to pass them as `geographies` to `census_compare_geographies`, or to make one call per state. A missing parent this tool has no input for is reported as such: the hint offers `geography_fips: "*"` when the wildcard would drop that parent, and otherwise says the level is out of reach. geography.json can list one level under several hierarchies (`new england city and town area` both under a combined NECTA and on its own; `american indian area/alaska native area/hawaiian home land (or part)` six ways on `dec/dhc` 2020); every entry is checked, the call runs when any accepts it, and the paging notice's scope suggestions come from that entry. When none accepts, the error describes the entry this tool's scope inputs (`parent_fips`, `county_fips`, `tract_fips`) can satisfy with the fewest changes, adding a parent ahead of dropping one; then one a `*` target would bring within reach; a parent out of reach is named only when no entry can be satisfied. So a NECTA (or part) with no parent needs `parent_fips` alone, not the combined NECTA its first entry names. When the entry reported also does not take a parent the call supplied, the error carries `unacceptedParents` and the hint names both changes — a NECTA (or part) under `county_fips` alone is told to add `parent_fips` and drop `county_fips` in one error, rather than meeting `parent_not_accepted` after the first fix.
- `parent_not_accepted` (ValidationError) — `parent_fips`, `county_fips`, or `tract_fips` names a parent the level does not sit within (a `tract_fips` on `tract` or `county`), which the Census API would answer with an opaque `400`. Thrown before the data query; the hint names the input to drop. For a level listed under several hierarchies this is the closest entry's verdict, as under `parent_required`: a NECTA under `parent_fips` is told to drop it, since the only other entry needs a combined NECTA no input can supply.
- `no_data` (NotFound) — the upstream query returned no rows; `204 No Content` is read as zero rows rather than an unparseable response. An offset at or past an existing set's `totalCount` instead returns an empty page with totals and a notice. Recovery retains predicate, sibling-table, geography-level, and literal FIPS-width guidance (at the levels that take a full GEOID, the width sentence is followed by one saying the full GEOID, with its digit count, is also accepted), adding applicable ACS publication guidance and boundary-vintage guidance as possible causes rather than a diagnosis; see "ACS publication coverage guidance" and "Boundary changes between vintages are named as a possible cause" below.
- `predicate_not_supported` (ValidationError) — a key in `predicates` is not a variable in this dataset+year. Validated against the cached `variables.json` before the data query, because the Census API's own rejection surfaces as a `400` naming the request URL and nothing about which key was wrong.
- `too_many_variables` (ValidationError) — the variable codes plus `NAME` and the label and record columns added for the dataset exceed the 50 columns the Census API accepts. Raised before the data request; the message states the most this query can carry (49 on ACS) and names the added columns. A table in `group`, and a listed code it returns, are not counted. Recovery: split the codes across calls of at most that many.
- `upstream_error` (ServiceUnavailable, retryable) — Census API returned an error, exhausted a transport failure, or exceeded the shared 50-second invocation budget or 40-second data ceiling within it. Attempts remain capped at 15 seconds or the time left, including response bodies. Local data-deadline errors carry `deadlineMs`, `elapsedMs`, and `retryAttempts`; total-call expiry carries the shared `deadlineMs`, `elapsedMs`, and `callDeadlineExceeded`. A response too large for one attempt can fail on every retry, so recovery offers a narrower geography or fewer variables as well as retrying; for a `group` query it names a narrower geography, or listing only the needed codes from the table in `variables` in place of `group`. Caller cancellation remains cancellation. See "Upstream deadlines" under Service notes.

**Annotations:** `readOnlyHint: true`, `openWorldHint: false`

### `census_compare_geographies`

**Description:** Compare one or more variables across multiple geographies at the same level — all counties in a state, all states nationally, or a named set of specific geographies — ranked on the value of one of them. Use for "compare median income across WA counties" or "which states have the most people below the poverty line." A count ranks geographies by size, not by rate: to rank a rate, rank a published percentage — `S1701_C03_001E` (percent below the poverty level, `acs/acs5/subject`), `DP03_0128PE` (the same percentage, `acs/acs5/profile`), or `DP04_0047PE` (percent of occupied housing units that are renter-occupied, `acs/acs5/profile`). Profile and subject tables reach tracts but not block groups. See "Rates rank through published percentages" below.

**Input:**
- `variables: string[]` — variable codes to compare (e.g., `["B19013_001E", "B19013_001M"]`); the ranking is on one of them, set by `sort_by`. Sent in the dataset's own spelling as in `census_query_data`, and held to the same column limit. Include MOE counterparts (`M` suffix) to get reliability context. An empty list, or one holding only blank codes, fails with a ValidationError ("At least one variable code is required.") before any request; unlike `census_query_data`, this tool has no `group`.
- `geography_level: string` — the level to compare across (e.g., `"state"`, `"county"`, `"tract"`). Use `census_list_geographies` to see valid values for the dataset.
- `within?: string` — FIPS of the parent geography to constrain results (e.g., state FIPS `"53"` to compare counties within WA only). Omit to compare all geographies at the level nationally. Use `census_resolve_geography` to get the FIPS. `"*"` works where it does for `parent_fips`.
- `within_county?: string` — county FIPS to constrain a tract or block-group comparison to one county inside `within` (e.g., `"033"`). `census_resolve_geography` returns this as `county_fips`. `"*"` works where it does for `county_fips`.
- `geographies?: string[]` — optional list of specific geographies to include; when provided, only these are returned. Omit to return all geographies at the level within `within` (or nationally). An entry matches a row's full GEOID (`"53033"` King County WA, `"06037"` Los Angeles County CA) or its bare level code (`"033"`). Prefer GEOIDs: they are nationally unique, so a list may span states, whereas a bare code matches that code under every parent the comparison leaves open — every state unless `within` names one, every county unless `within_county` does. A GEOID is easiest taken from a row's own `geography_geoid`; from `census_resolve_geography`, concatenate `state_fips`, then `county_fips` when present, then `fips_summary` — a tract GEOID is state + county + tract, not state + tract. Entries that match no row, and bare codes that matched more than one geography (the notice offers whichever of `within` and `within_county` is still open), are named in the response notice; a list that matches nothing at all throws `no_data` rather than returning an empty ranking.
- `predicates?: Record<string, string>` — dataset-specific filter values keyed by variable code, applied to every geography in the comparison. Normalized as in `census_query_data`; a `"*"` value puts each geography on one row per category, which fails with `ambiguous_rows`. See "Predicate filtering" below.
- `dataset?: string` — dataset to query (default: `"acs/acs5"`), resolved as under "Dataset codes resolve case and two-part shorthand"
- `year?: number` — vintage year (default: latest available)
- `sort_by?: string` — variable code to rank on (default: the first code in `variables`), matched regardless of case like the variables. It must name one of the requested codes, compared uppercased, or the call fails with `sort_by_not_requested` before any request; once the cache has loaded, it maps to the same dataset spelling its code does, which `sortVariable` echoes. The ranking is on that code's own value, so a count ranks by size and only a published percentage ranks by rate.
- `sort_dir?: 'asc' | 'desc'` — sort direction (default: `'desc'`)
- `limit?: number` — max geographies to return: an integer of 1 or more (default: 50). A value over 500 returns 500 geographies and the notice says so; see "A limit over the cap is served at the cap". When results are truncated, `totalCount` says how many geographies matched.
- `offset?: number` — rows to skip in the sorted matched subset: an integer of 0 or more (default: 0). It counts rows, not competition ranks; a page can begin within a tie. An offset at or past `totalCount` returns an empty page rather than `no_data`.

**Output:** `{ variable_labels, rows: [{ geography_name, geography_fips, geography_geoid, variables: { [code]: { estimate, moe?, suppressed, suppression_reason?, open_ended?, flag?, value? } }, applied_filters?, record?, rank, scope_rank? }] }`, with `variable_labels` and its `content[]` legend as `census_query_data` states them. Enrichment carries `totalCount` after the geography filter but before offset/limit, `truncated` when more matched rows remain, optional `nextOffset` only then, `sortVariable`, and optional `notice`. A nonempty `geographies` filter also adds each row's `scope_rank` among all fetched geographies before that filter and enrichment `scopeCount` for that fetched set; without the filter, both fields are absent. The fetched scope follows `within`, `within_county`, dataset, year, and predicates, so it is not necessarily national or complete beyond what the dataset publishes.

Equal numeric estimates share competition ranks (`1, 2, 2, 4`) in either sort direction, with GEOID ordering ties deterministically. Both subset `rank` and full-scope `scope_rank` are assigned before paging. Open-ended boundaries participate by their numeric figure. Nonnumeric/suppressed rows follow every number with sequential ordinals, not a shared numeric rank. When no fetched row carries a number, upstream order is preserved and the notice says ranks are only return-order ordinals. A page boundary inside a numeric tie group produces a notice without increasing `limit`.

`geography_fips` enables follow-up queries with the same parents; nationally unique `geography_geoid` works in the `geographies` filter. Suppression reasons and `record` use the query tool's shapes. A comparison with several records per geography fails with `ambiguous_rows` rather than assigning several ranks to the same geography.

**Errors:**
- `missing_api_key` (Unauthorized) — `CENSUS_API_KEY` not configured or invalid; raised as in `census_query_data`.
- `sort_by_not_requested` (ValidationError) — `sort_by` names no code in `variables`, so every row would tie and the Census return order would be labelled a ranking. Raised from the input alone, before any request; the error carries `sortBy` and the requested `variables`. Recovery: set `sort_by` to a requested code, or add the code to `variables`.
- `ambiguous_rows` (ValidationError) — the dataset publishes several records per geography and the comparison pinned none, so every geography would occupy several ranks with different values. Raised after the data query, from a count of rows per full GEOID, so two same-numbered counties in different states are not read as a duplicate. The error carries the record columns and the values each took; the recovery hint names the one to add to `predicates` and the code that selects it. On a dataset that declares no filter dimension the rows differ only in `GEO_ID` (`geoinfo` 2020 ZCTAs), no predicate pins one, and the hint says to compare a vintage that publishes one row per geography.
- `geography_not_supported` (ValidationError) — the geography level does not exist in this dataset+year. Thrown before the data query, from the dataset's own geography metadata. Recovery: call `census_list_geographies`.
- `parent_required` (ValidationError) — the level requires a parent the request did not supply, or a `"*"` `within`/`within_county` the level's hierarchy does not wildcard (as for `census_query_data`). Thrown before the data query; the message names the missing parent levels and the recovery hint names `within` or `within_county`. A level listed under several hierarchies is checked against each, as in `census_query_data`, with reachability judged against this tool's own inputs: it has no tract input, so an entry that needs a tract is out of reach here. An AIANNH (or part) comparison under `within` and `within_county` is therefore told to drop `within_county` (the state-only entry), where `census_query_data` under the same scope is told to add `tract_fips`. A parent to drop alongside the ones to add is named in the same error, as in `census_query_data`.
- `parent_not_accepted` (ValidationError) — `within` or `within_county` names a parent the level does not sit within, which the Census API would answer with an opaque `400`. Checked against the level's own `requires` list, so the `*` wildcard relaxes which parents are mandatory but never which are allowed.
- `year_not_available` (ValidationError) — the dataset cannot be queried for the requested vintage. Raised from `DATASET_AVAILABLE_YEARS` before the handler's first request.
- `variable_not_found` (NotFound) — the Census API rejected a variable code as unknown for this dataset+year, mapped the same way as in `census_query_data`, sibling recovery included.
- `too_many_variables` (ValidationError) — the same column count as `census_query_data`, raised before the data request with the most this comparison can carry.
- `variables_unavailable` (ServiceUnavailable, retryable) — required variable metadata could not be fetched or parsed within the shared invocation budget.
- `predicate_not_supported` (ValidationError) — a key in `predicates` is not a variable in this dataset+year, validated before the data query.
- `no_data` (NotFound) — no geographies returned, or the `geographies` filter matched no row. Recovery preserves predicate/sibling-table guidance and literal FIPS/full-GEOID advice, adding applicable ACS coverage rules and boundary-vintage guidance as possible causes. An offset beyond a nonempty matched subset returns an empty page with totals and a notice instead.
- `upstream_error` (ServiceUnavailable, retryable) — Census API returned an error, exhausted a transport failure, or exceeded the shared 50-second invocation budget or 40-second data ceiling within it, as in `census_query_data`.

**Annotations:** `readOnlyHint: true`, `openWorldHint: false`

## Design Decisions

### Geography resolution is a mandatory first step, not a hidden convenience

`census_query_data` and `census_compare_geographies` require FIPS codes. They do not resolve place names internally. This is a deliberate choice:

1. Resolution is non-trivial — "King County" exists in multiple states. The resolution step should be visible to the agent so it can see and confirm what geography it's actually querying.
2. Hiding resolution inside `census_query_data` would duplicate `census_resolve_geography`'s function and make errors harder to diagnose — a name resolution failure mid-query is harder to surface cleanly than a failed pre-query resolution step.
3. Agents that already have FIPS codes (from a prior resolution call or from other data) skip the extra step without any penalty.

`census_resolve_geography` is the mandatory bridge from place names to FIPS. The workflow is: `census_resolve_geography` → FIPS codes → `census_query_data` or `census_compare_geographies`.

### Name variants are retried against TIGERweb, not aliased

A caller's spelling that maps one-to-one onto a TIGERweb name — lowercase, "Saint" for "St.", no accent, a CBSA name from an earlier delineation — resolves through retries on a zero-row lookup rather than a static alias table. An alias table is data per TIGERweb vintage and drifts with each one, and it cannot follow the 2023 delineation's reassignment of CSA codes; the retries read whatever the current vocabulary is. Retries run only after every level's as-given query found nothing, so they never displace a real match.

### New York City boroughs are a fixed table, read as the county's query term

The borough → county map is the resolver's one static alias table for place names. It does not have the drift problem above: the five boroughs have been coextensive with their counties since 1914, when Bronx County was split from New York County (Richmond borough was renamed Staten Island in 1975, the county keeping its name), and TIGERweb confirms the one-to-one layout. The mapping replaces the county level's query term rather than running as a no-match retry, because a retry would be preempted by any place row that merely contains the name, and it is never applied at the place level, where "Manhattan" read as "New York" would answer with New York city. A recovery hint alone would cost the caller a round trip for a mapping the server knows with certainty, so the result resolves and a `notice` discloses the substitution on both surfaces.

### A CDP answers a name only when no incorporated place or county has it

Adding the CDP layer to the place level as a plain peer of incorporated places turned many names that v0.4.0 resolved into ambiguities or CDPs. Replaying both matchers offline over every incorporated-place, CDP, and county name in TIGERweb: 122 of 34,556 state-scoped names ("Mountain View, CA", "Burbank, CA", "Paradise, CA") and 1,122 of 22,187 bare names ("Tacoma", "Atlantic City") went from resolving to `ambiguous_name` on a same-named CDP, and 204 state-scoped names ("Arlington, VA", "San Juan, PR") moved from their county to a CDP. Ranking a CDP below an incorporated place and an exact county keeps all but 11 of those state-scoped v0.4.0 answers — each of the 11 was a row that only contained the name ("Chester, VA" answered Chesterfield County) — while the 12,218 state-scoped names v0.4.0 missed, nearly all of them CDPs, still resolve.

### A resolved ZCTA is never cbp's `zip code`

ZCTAs and ZIP codes are different units: `cbp` publishes ZIP-level rows under the ZIP itself, including ZIPs with no ZCTA. So a ZIP resolves only to `zip code tabulation area`, a ZCTA miss says it was checked only as a ZCTA, and the `cbp` `zip code` path stays pass-through with no resolver in front of it — validating a ZIP against the ZCTA layer would reject real `cbp` rows such as `98111` and the "Unclassified" `99999`.

### Why not accept human-readable concepts directly in `census_query_data`?

Early consideration was to make `census_query_data` accept a `concepts` parameter like `["median household income", "poverty rate"]` and resolve internally. This was rejected because:

1. Resolution is ambiguous — "median income" matches 34 variables across different subgroups (by race, household size, etc.)
2. The resolution step is genuinely useful to surface to the agent, not hide — the agent should see and confirm the codes it's querying
3. It conflates two operations that benefit from being separate: search (exploratory) and query (precise)

The workflow is: `census_search_variables` → agent picks codes → `census_query_data`. This is one extra step but avoids silent mismatches.

### ACS publication coverage guidance

ACS products have different publication rules. `describeAcsCoverage()` in `src/mcp-server/tools/acs-coverage.ts` supplies the same guidance to both data tools' empty-result recovery and unmatched-member notices, including comparisons whose entire requested subset is absent. It names coverage as one possible cause, never proof a code is invalid or an area's population is below a threshold; no population lookup is added. Fully matched lists, ordinary five-year detailed/profile data, and non-ACS datasets receive no invented coverage warning.

| Dataset | General publication rule | Broader-coverage alternative |
|:--|:--|:--|
| `acs/acs1` | Areas of 65,000 or more people | `acs/acs5` |
| `acs/acs1/profile`, `acs/acs1/cprofile` | Areas of 65,000 or more people | `acs/acs5/profile` |
| `acs/acs1/subject` | Areas of 65,000 or more people; selected tables have additional subgroup rules | `acs/acs5/subject` |
| `acs/acsse` | Areas of 20,000 or more people | `acs/acs5` |
| `acs/acs5/cprofile` | Areas of 5,000 or more people | `acs/acs5/profile` |
| `acs/acs1/spp` | Area population of 500,000 and subgroup population of 65,000 | `acs/acs5` |

Continuity and metropolitan-area exceptions can apply. Changing datasets does not translate variable codes: discover corresponding variables with `census_search_variables` or `census_get_variable`. Switching from comparison profiles to data profiles does not preserve comparison history. The explicit dataset choice keeps these limits visible, while `census_list_geographies` identifies supported levels rather than promising publication for every area at them.

### Boundary changes between vintages are named as a possible cause

A code `census_resolve_geography` returns is drawn on current boundaries, so a vintage drawn on others can have no row for it. `describeBoundaryChange()` in `src/mcp-server/tools/boundary-vintage.ts` words two such changes for both data tools' empty-result recovery and unmatched-code notices, as one possible cause beside a wrong code and never as a diagnosis from the empty result alone.

- **Tracts.** When a call names a tract (a tract code, a `tract_fips`, or a `geographies` entry carrying one) at `tract`, `block group`, or `block` on a vintage before 2020, the text says the vintage publishes the tracts of the 2010 Census, or of the 2000 Census through 2009 (`acs/acs5` 2009, `dec/pl` 2000), not the 2020 tracts the resolver returns, since the 2020 Census split, merged, or renumbered many. The step is `geography_fips "*"` at the tract level with the same parents in `census_query_data`, and omitting `geographies` in `census_compare_geographies`. A tract-level `"*"` names no tract and gets no such text. The width and GEOID guidance follows as the second cause. `dec/pl` 2000 also lists a whole-number tract, whose 6-digit code ends in 00, by its first 4 digits (Tract 71 in King County is `0071`, GEOID `530330071`; 40,786 of the 66,304 tracts in the 50 states, DC, and Puerto Rico are listed that way, and none of the other 25,518 six-digit codes ends in 00). A 6-digit code ending in 00 is therefore sent as its 4-digit form, as a `geography_fips` tract member, as `tract_fips`, as the tract inside a full tract or block GEOID, and in a `geographies` entry, and the 9-digit tract and 13-digit block GEOIDs carrying it are read as GEOIDs. Rows keep the upstream code. The notice, and the `no_data` hint ahead of its causes, says `dec/pl (2000) lists a census tract whose 6-digit code ends in 00 by its first 4 digits, the form its rows and GEOIDs carry, so "007100" was read as "0071".`
- **Connecticut counties.** A county code in the scheme the vintage does not publish (a planning region 110–190 through 2021, a pre-2022 county 001–015 from 2022) is named with the scheme the vintage does publish. Tracts and county subdivisions kept their codes across the 2022 change (881 tracts checked) and changed only county, so below the county level the step is `geography_fips "*"` with `county_fips "*"` and `parent_fips "09"` (`within_county "*"` with `within "09"` in the comparison), and at the county level it lists the counties.

The resolver carries the same facts forward: every result with a `tract_fips` has a notice that it is a 2020 tract, and a Connecticut one adds the planning-region sentence.

### Data profiles (DP tables) vs detailed tables (B tables)

ACS5 has four sub-table types. Data profiles (`acs5/profile`, DP-prefix codes like `DP03_0062E`) cover the most common social, economic, demographic, and housing metrics with ~1,400 variables that are more human-readable than B-table codes. Detailed tables have 28K+ variables for cross-tabulated deep dives. The design doesn't hide this distinction — `census_search_variables` searches across the specified sub-table, and the tool descriptions explain when each is appropriate.

### Dataset codes resolve case and two-part shorthand

Every tool with a `dataset` input runs it through `resolveDataset()` in the variable cache, beside the registry, before the year default, validation, or any request. The code is trimmed and lowercased, then matched exactly; every registered code is lowercase, so each value accepted before resolves to itself. A single segment resolves when it is the second segment of exactly one two-segment code (`acs5` → `acs/acs5`, `pl` → `dec/pl`), and a registry test fails if two two-segment codes ever share one. Each tool validates, requests, takes its default year from, and echoes the resolved code, so `"pl"` searches `dec/pl` 2020, that dataset's own latest vintage. A blank optional `dataset` stays `acs/acs5`; a blank required one is `dataset_not_found` worded as a missing code.

A third segment (`profile`, `subject`) never resolves, and its error's recovery hint names the registered codes that end in it. Resolving any leaf unique across the registry was the alternative, and was rejected because uniqueness does not last: `subject` was unique until `acs/acs1/subject` joined `acs/acs5/subject`, and adding a dataset would have broken an input that used to work. Fuzzy and prefix matching and alias tables ("5-year ACS") were left out for the same reason — each widens what a code can mean.

### Why `census_compare_geographies` instead of multiple `census_query_data` calls?

The comparison workflow — ranking states by their poverty percentage, comparing counties on median income — requires one variable across many geographies. `census_query_data` pages rows in GEOID order; `census_compare_geographies` makes the same single wildcard request against one dataset, then sorts and ranks before applying offset and limit. It reaches the middle of a ranking without requiring the caller to collect and sort every GEOID-ordered page. A named subset retains both its own ranks and the fetched scope's ranks. It has no multi-dataset path: comparing variables from two datasets takes one call per dataset.

### Rates rank through published percentages

`census_compare_geographies` ranks on one variable's value. Ranking a count ranks size: on `acs/acs5` 2024 states, the ten largest poverty headcounts (`B17001_002E`) and the ten highest poverty rates share no state, and California is first by count and 24th by rate. The Census publishes the rate itself: `S1701_C03_001E` (`acs/acs5/subject`) and `DP03_0128PE` (`acs/acs5/profile`) for percent below poverty, `DP04_0047PE` (`acs/acs5/profile`) for percent renter-occupied. Each equals the rate computed from its B-table count and universe to 0.1, ranks through the tool unchanged, and carries a Census margin of error the tool pairs by the usual `E`→`M` swap. Profile and subject tables stop at tract, so a block-group rate has no published column.

A derived-ratio sort (`sort_ratio: { numerator, denominator }`) was considered and not built. It would reach block groups and ratios the Census does not publish, but it adds an input, a derived output field, and an approximated margin of error (the ACS handbook proportion formula with its ratio fallback) where the published percentage carries the Census's own.

### Land area is a dataset, and density is the caller's division

`geoinfo` publishes land area, water area, and the internal point of every geography level from `us` down to block group and ZCTA, 2020 through 2025, in the query shape the data tools already send: `AREALAND` and `AREAWATR` in square meters, `AREALAND_SQMI` and `AREAWATR_SQMI` in square miles, `INTPTLAT` and `INTPTLON`. It is registered like any other dataset. It declares no filter dimension (`GEOCOMP`, the only required predicate, stays out of the dimensions, so rows carry no `applied_filters`) and publishes no margins of error. The server returns no density: the `census_list_datasets` entry carries the recipe, which is to query the count and `AREALAND_SQMI` at the same level and codes, pass the same explicit `year` to both calls since each dataset defaults to its own latest vintage, and divide. Areas start with 2020, on that decade's tract boundaries; a tract count from 2019 or earlier is on 2010 tracts, so a GEOID join drops every tract the 2020 Census redrew and pairs the codes it kept with 2020 areas. A water-only tract has an `AREALAND_SQMI` of 0. The 2020 vintage's repeated delineations are covered under "Several records per geography are labelled, not collapsed", and the 2021 and 2022 vintages carry 32,923 of the 33,774 2020 ZCTAs, where 2023 onward carries all of them.

### Wildcard results are capped and paged

A `census_query_data` wildcard once returned every row: 3,222 counties with an estimate and its margin ran to 1.45 MB of `structuredContent` and 1.1 MB of `content[]` text, about 800 bytes a row across both. It now returns at most `limit` rows (default 50, cap 500 — the same bounds as `census_compare_geographies`; a larger `limit` is served at the cap, see "A limit over the cap is served at the cap"), and `offset` reaches the rest. The rows are sorted by `geography_geoid`, then by the code of each `record` column, before slicing. The Census documents no row order, so the sort is what makes pages consistent. The second key exists because the upstream order within one geography is not stable: identical `cbp` 2023 King County `NAICS2017=*` requests minutes apart put `11521` before `1151` in one response and after it in the next. Each page is a request of its own, so keeping the order the Census sent could repeat one category on the next page and skip another. Code order also lands `pep/charv` April (`4`) before July (`7`). The cap counts rows rather than geographies, because the bytes are per row: `pep/charv` returns two records per geography and a `"*"` predicate one row per category.

`offset` is a slice of the one upstream response the handler already fetches — no upstream cursor, no cache. A cap without it would strand rows that are reachable today: Los Angeles County has 2,498 tracts, which have no narrower parent this tool can express. King County's 1,545 block groups narrow by `tract_fips` — the notice offers it once the county is set — but a county-wide list still spans four pages at `limit: 500`. Comparison pages instead follow numeric ranking, so they answer a different ordering need. `totalRows` remains rows returned and `totalCount` rows matched. `truncated` means more rows remain after this page, not that offset omitted earlier rows; optional `nextOffset` is offset plus rows returned only when more remain. Range, last-page, and past-end notices are generated independently of that flag. An offset at or past the end returns no rows with `totalCount` and a notice, not `no_data`, since the data exists. `format()` renders only the rows it is given, so totals and continuation appear in the enrichment trailer.

The same continuation contract applies to all four paged tools: query rows, comparison ranks, variable search, and predicate values. Each forms its complete match set and stable ordering before slicing; totals do not change with offset. Search keeps code-tier matches ahead of keyword matches, predicate values stay in code order, and comparison offsets count rows rather than competition ranks. Final and past-end pages have `truncated: false` and no `nextOffset`; a genuine no-match keeps the tool's existing recovery. Paging notices retain partial-term, dictionary/source, industry/geography, and unmatched-member guidance.

### A geography_fips list is several geographies

The Census API takes a comma-separated list in `for=` (`state:06,53`, `county:033,061` under `in=state:53`), and `census_query_data` passes `geography_fips` through, so a list returns one row per listed geography at the level, in GEOID order rather than list order, capped and paged exactly as a wildcard is. Measured on acs/acs5 2024 (api.census.gov, 2026-10-29): the API trims each member (`"06, 53"` is two rows), collapses a repeat (`"06,06"` is one), answers a list with every member unknown with `204`, and rejects an empty or `"*"` member (`"06,"`, `"06,*"`) with a `400` naming the `for` argument. The geography check reads any value other than `"*"` as concrete, so a list needs the parents a single code needs: `"033,061"` without `parent_fips` is `parent_required`, as the API's own "ambiguous geography" `400` would be.

Lists are documented rather than rejected: they return correct rows at every level probed, and rejecting them would turn calls that answer today into errors. What a list got wrong was silence — the API drops a member it publishes nothing for and answers with the rest, so `"06,99"` and the unpadded `"06,6"` returned California alone with `totalCount` 1 and nothing to say a code was missing. The notice now names each member no row came back for, judged against every row the query matched rather than the page (`"53,06,41,16,32"` at `limit: 2` names nothing) and compared to each row's `geography_fips` after trimming, as the API trims. A single code and `"*"` get no such notice; an empty or `"*"` member is left to the API's `400`, which already names the argument. On the `POPGROUP`-split tables a member whose group sits in a sibling table has no row for the same reason, so the unmatched-code notice is followed by the table-split guidance (dec/ddhca `T02002_001N`, `POPGROUP` `1360`, `"02,53"` returns Alaska alone and names `53`).

### Full GEOIDs are read in the tool

`geography_geoid` is the identifier `census_compare_geographies` takes, so a caller holding a row's GEOID tried it as `geography_fips` and got no row: no level answers its GEOID form upstream. At the nine levels whose GEOID is a fixed chain of parent codes and the level's own code (county, place, school district (unified), economic place, congressional district, county subdivision, tract, block group, block), `census_query_data` reads a member that is exactly the GEOID's width and all digits as its parents plus the level code, so `"53053"` at `county` is `"053"` under `parent_fips "53"`. The parents can be omitted when every listed GEOID names the same ones, and must match when given; a GEOID naming a different parent is sent as written, gets no row, and the hint names the code and parents to send. Bare codes, `"*"`, a `"*"` parent, and other levels are unchanged. The reading is in the tool rather than the service because only the tool knows the call's scope, and it applies only when every parent it carries is concrete and matches. Reading a GEOID against a conflicting or wildcarded parent would send a different query than the caller wrote, and since no level answers a GEOID upstream, nothing a call did before changes meaning. An all-GEOID list spanning several states or counties cannot be one request, so `parent_required` points to `census_compare_geographies`'s `geographies` filter or one call per state. On `dec/pl` 2000 the tract-bearing GEOIDs have a shorter form too, 9 digits for a tract and 13 for a block, because only that vintage lists a whole-number tract by 4 digits; the rule is keyed on dataset and year, and the `no_data` GEOID sentence names the shorter width there. Unmatched-code notices quote each member as the caller wrote it, with the example `"053"` or its full GEOID `"53053"`.

### Tool inputs accept unadvertised aliases that follow names the server emits

Callers carry argument names from the server's own output and from sibling tools into the next call: `dataset_id` (the key `census_list_datasets` returns) for `dataset`, `geography_type` (the resolver's input) for `geography_level`, `fips_summary` and `state_fips` (resolver output fields) for `geography_fips` and `parent_fips`, `within` (the comparison's input) for `parent_fips`, `keyword` for `query`. Seven tools (all but `census_list_datasets`) map such keys onto the input they mean through definition-level `inputAliases`, so a call that would fail on `Unrecognized key` answers instead. An alias matches exactly (no case folding, so `Keyword` stays rejected) and is not advertised: `tools/list` is unchanged. An alias sent beside its target, or two aliases of one target, is rejected naming them as aliases, since taking one value would silently drop the other. A name earns an alias only when the server emits it or a sibling tool takes it. Renaming `dataset_id` in the `census_list_datasets` output was rejected: renaming an output field breaks callers that read it, where an input alias breaks none.

### A limit over the cap is served at the cap

The four paged tools advertised their cap as the schema `maximum` and rejected a larger value with `-32602`, which cost every over-cap caller a round trip for an answer the server could already give, and put a bound in the schema where count inputs carry only a default and a minimum. With `CENSUS_CLAMP_LIMITS` on (the default), a `limit` over the cap is served at the cap: `census_query_data` and `census_compare_geographies` 500, `census_search_variables` 3,000, `census_list_predicate_values` 10,000. The caps sit where a page stays near 1 MB per surface: the data tools' widest `variables` list lands there at 500 rows, search at 3,000 variables, and no predicate list is longer than 10,000. The notice opens with `limit N is over the C-<unit> cap, so this page holds up to C <units>.` ahead of the paging sentence on both surfaces, one info line is logged, and the counter `census.limit.clamped` (attribute `mcp.tool.name`) goes up by one. `tools/list` advertises `{"type":"integer","minimum":1}` with no `maximum`, and the description reads "Default 50; a larger value returns at most 500 and says so." The schema is `z.number().min(1)` with a `.check()` that rejects a non-integer, not `.int()`, which also enforces `Number.MAX_SAFE_INTEGER` and would reject `1e20` instead of clamping it. With the switch off, each cap is advertised as `maximum` and cap + 1 is rejected with `-32602` as before ("Default 50, max 500."). A malformed value stops startup. Every "raise `limit`" hint names the tool's current cap.

### Notices quote caller text literally

The framework renders a `notice` into `content[]` as a live Markdown block quote, escaping nothing, while `structuredContent.notice` carries the raw string. Every notice that quotes a caller's `query`, `filter`, `geographies` entry, or `geography_fips` code — or an upstream label, such as the applied default a filter-dimension notice names — would let `*x*`, `` `y` ``, or `[z](w)` render as emphasis, code, or a link. `census_search_variables`, `census_list_datasets`, `census_list_predicate_values`, `census_compare_geographies`, `census_query_data`, and `census_resolve_geography` therefore render the notice through `renderNotice` (`src/mcp-server/tools/notice-trailer.ts`): each line of `escapeMarkdownInline(notice)` quoted, so a CommonMark parse of `content[]` reads back exactly `structuredContent.notice`. No notice carries authored Markdown, so escaping the whole string loses nothing. Escaping inside the handler was rejected because it puts the backslashes into `structuredContent.notice` as well. `census_get_variable` keeps the default render: its notices are built from dataset-validated codes. The resolver's notices quote TIGERweb place and subdivision names and the `"*"` a tract listing takes, so they go through it.

### Margin-of-error inference is scoped to the ACS family

`variables.json` omits ACS's `M`-suffix margin-of-error codes even though the data API serves them, so the variable cache infers each `B…E` estimate's `B…M` sibling and synthesizes an entry for it. That `E`/`M` pairing is an ACS table convention, not a Census-wide one: `pep/charv` has `UNIVERSE`, `AGE`, and `MEDAGE`, `ecnbasic` has `INVTOTE` and `INVWIPE`, and `cbp` has `STATE` — ordinary codes that happen to end in `E` and have no margin of error at all. Applied to those families the inference invented codes (`UNIVERSM`, `INVTOTM`, `STATM`) that do not exist upstream, and `census_get_variable` resolved them to fabricated "Margin of Error — …" entries instead of reporting `variable_not_found`.

Both the inference and the synthesis are gated on `publishesMarginsOfError()`: the `acs/` prefix `isAcsDataset()` tests, minus the comparison profiles (`acs/acs5/cprofile`, `acs/acs1/cprofile`). Those publish no margins at all — the data API answers `CP03_2024_062M` with HTTP 400 — so an inferred `moe_code` there would name a column that cannot be queried. They still write ACS sentinels, so sentinel decoding stays on `isAcsDataset()`. Inferring `M` only when a code's `attributes` names it was the alternative, and was rejected because `acs/acs1` 2024 `B19013_001E` lists no attributes while the API serves its margin.

Within ACS the inference also skips every column with `group: "N/A"`. Those are the geography columns `variables.json` lists beside the estimates — `STATE` and `PLACE` on every vintage, `AITSCE` and `LSAD_NAME` on the older ones. They end in `E` but have no margin: `/data/2024/acs/acs5/variables/STATM.json` is a 404.

A synthesized entry reads as the Census's own per-variable record does, without fetching it. The label replaces the estimate's `Estimate` segment with `Margin of Error` wherever it sits: first on current vintages (`Estimate!!…`), later on older ones (`Total!!Estimate!!…` becomes `Total!!Margin of Error!!…` on 2010 `acs/acs5/subject`). A current profile's `Percent!!` becomes `Percent Margin of Error!!`. The predicate type is `float` for a fractional estimate and `int` otherwise, since the year medians are typed `string` while their published margins are `int`. `attributeOf`/`attributeType: "MARGIN_OF_ERROR"` name the estimate. An `M` code `variables.json` does list gets the same two attribute fields. The earlier `Margin of Error — Estimate!!…` label kept the word "estimate", so an `M` code matched one more word of an "estimate" query than its own estimate and took the whole first tier of the results. The published label has the same effect through its own prefix: "Margin", "of", and "Error" are words the estimate's label lacks, so "median value of" put `B25077_001M` alone in the first tier. Search therefore matches every margin of error, synthesized or listed, on its estimate's label (see "Variable search is client-side, not a Census API feature").

`CensusApiService.parseResponse` carries the same ACS gate when it pairs a requested `E` value with a requested `M` value into `.moe`. That path never fabricated anything — it only pairs codes the caller explicitly requested, and no non-ACS dataset in the registry currently has both a `<stem>E` and a `<stem>M` variable for it to mispair. It is gated anyway so the two services tell one story about where the convention holds, rather than the cache reporting no margin-of-error relationship while a query attaches one.

### Predicate filtering: a generic map, with unset dimensions reported rather than guessed

Several datasets mark variables `required` in `variables.json` — `NAICS2017`/`NAICS2022`, `LFO`, `EMPSZES`, `RCPSZES`, `TAXSTAT`, `TYPOP` on the business datasets, `SEX`, `AGE`, `POPGROUP`, `HISP`, `YEAR` on `pep/charv`, and `POPGROUP` on `dec/ddhca`, `dec/ddhcb`, and `acs/acs1/spp`. The Census API does not enforce them. A query that omits one succeeds and substitutes the API's own default for that dimension: `cbp` establishments in King County is 70,376 with no `NAICS2017` and 577 with `NAICS2017=5112`. Registering the business datasets without a way to send these would answer "how many software companies are in King County" with the all-industries total.

`predicates` is a `Record<string, string>` on both data tools rather than dataset-aware named parameters (`naics`, `size_class`) because the codes are vintage-specific, not just dataset-specific — `cbp` 2023 takes `NAICS2017` while `cbp` 2012 takes `NAICS2012`, and `nonemp` 2023 takes `NAICS2022`. Named parameters would need a hand-maintained dataset × year × parameter mapping that drifts, and would add seven dead optional fields to every ACS query. The map is validated against the dataset's own cached `variables.json` instead, so it stays correct across vintages with no table to maintain.

An unset required predicate is reported through `ctx.enrich.notice()`, not thrown as an error. Erroring was rejected because it was unrecoverable for most of these dimensions: `variables.json` publishes a value list for `NAICS*` and `POPGROUP` only, so a caller told to supply `LFO` or `EMPSZES` had no endpoint to learn what they accepted — `census_list_predicate_values` now closes that gap by enumerating the rest against the live data endpoint. Erroring would also break every existing `pep/charv` and `dec/ddhca` query, which is the only form those datasets are reachable in today. The notice reaches both `structuredContent` and `content[]`, attached to the number itself, and names each unset dimension with its label.

What the notice does *not* say is that the value is an all-categories total, because the substituted default is not one shape. `cbp` defaults `NAICS2017` to `00`, the all-industries total. `pep/charv` defaults `YEAR` to 2020, so an unfiltered `POP` query against the 2023 vintage reports 2020 rather than a sum across 2020–2023. Calling both an aggregate would misreport the second, so the wording says only what holds for both: the API supplied the default, so no value is scoped to a category the query chose. `YEAR` still cannot be echoed back per row — naming it in `get=` flips the query from applying the default to enumerating all four vintages — so the notice names it as a dimension whose applied value is not visible.

The duplicate rows `pep/charv` returns for one geography are a separate mechanism from the defaults, and are covered below.

`GEOCOMP` is excluded from the report: every Census dataset declares it — checked across every registered dataset — its default is the whole geography, and listing it beside real filter dimensions on every ACS query would train readers to skip the notice.

An unknown predicate *key* is an error (`predicate_not_supported`), validated client-side, because that case is both unambiguous and fully recoverable. The Census API does reject it with a `400`, but the message that reaches the caller carries only the request URL and the status — never which key was wrong. An unknown predicate *value* is not rejected at all: it comes back as `204 No Content`, indistinguishable from a geography with no data, which is why the `no_data` recovery hint names the supplied predicates alongside the unset ones. The hint names an unset dimension only where its default can empty a result: `ecnbasic`'s NAICS dimension, which defaults to one sector a county often lacks, and `POPGROUP` on `dec/ddhca` and `dec/ddhcb`, which defaults to one group a table can leave unpublished. Every other default is an all-categories total (or `pep/charv` `YEAR` 2020, which always publishes), so naming it would send the caller to set a dimension that changes nothing. A two-digit NAICS value `31`, `32`, `33`, `44`, `45`, `48`, or `49` under any `NAICS####` key on `cbp`, `ecnbasic`, or `nonemp` adds a line naming its range (`48` → `"48-49"`), since those datasets publish the three sectors only as `31-33`, `44-45`, and `48-49`. The value is named rather than rewritten: `49` alone is narrower than `48-49`, so swapping one for the other would answer a question the caller did not ask.

The map is normalized before any of this. Keys are uppercased, because no supported dataset defines a lowercase variable and the Census API matches keys case-sensitively, so `naics2017` has exactly one meaning. Values are trimmed, and a blank or whitespace-only value is dropped. Sent upstream, `NAICS2017=` is a group-by over every category, the same as `*`, while a blank is what a form-based client sends for a field it left empty; treating it as omitted matches the "blank is treated as omitted" rule `parent_fips`, `county_fips`, `within`, `within_county`, and `within_naics` already follow, and the unset notice then names the default the API applied. Rejecting it was the alternative, and would have added an error reason for a value the convention already defines.

`*` is kept, because a per-category breakdown of one geography is a real query. Its rows are labelled rather than collapsed — see "Several records per geography are labelled, not collapsed".

### Dictionary value lists are checked against published rows

A `values.item` map in `variables.json` is a classification the Census shares across products, not a record of what one dataset publishes. `dec/ddhca` declares 5,543 `POPGROUP` codes and serves 2,996; `cbp` declares 6,694 `NAICS2017` codes and serves 2,003; `pep/charv` declares 5,545 `POPGROUP` codes and serves 12. Returning the declared list unqualified handed callers dead codes — most sharply `dec/ddhca` `POPGROUP` `001` "Total population", the top hit for the obvious keyword and a code that returns nothing at any geography.

The check is one wildcard group-by per dimension, cached for the discovery TTL. What lands in `get=` decides what it answers from: a dimension's own label column can be served from the dictionary, so a label-only request reports every declared code, while naming one of the dataset's measure columns forces the read against the data file and answers with the published set. Coverage is per table. On `dec/ddhca` the one-cell total-population table `T01001` publishes 2,996 groups, and each sex-by-age table a subset of them, so the probe takes a measure from the table with the fewest cells, which is the widest set the dataset serves. Any other measure in that table gives the same answer, and on `cbp`, `nonemp`, `ecnbasic`, and `pep/charv` every measure in the dataset does.

The sex-by-age tables do not nest among themselves, though: `T02001`, `T02002`, and `T02003` publish 295, 573, and 551 groups at `us` with none in two of them. On `dec/ddhcb` every table belongs to such a family, so no single table holds every group — `T03001`, the coarsest, publishes 1,497 of 2,996 nationally and would withhold `1360` (Alaska Native alone), which Washington publishes in `T03002`. When the coarsest table belongs to a family (see "Tables that split population groups are named, not probed"), the probe unions one measure from each table of the dataset's smallest family instead: `T04001_001N` and `T04002_001N`, two requests per cache refresh, giving the 2,996. Each `dec/ddhcb` family splits the same 2,996, so the two-table tenure family is complete and costs half what the four household-type tables would. One request cannot union them: a multi-table wildcard returns only the first-listed table's groups, and a wildcard on `GEO_ID` or `NAME` answers from the dictionary. Every other dataset keeps its one probe. A union with one empty answer is treated as a failed check, since half a union would withhold every group the silent table publishes. The two probes share one abort: the first to fail ends the other, both are awaited before the call answers, and the failure reported is the one that ended the check, so a refused key still reads as the key rather than as the sibling it cancelled.

The national scope is an upper bound rather than a per-geography answer: `dec/ddhca` serves the same 2,996 groups in WA, CA, NY, and TX, and `cbp` serves 1,827 of its 2,003 national codes in WA — every sub-national set checked is a subset of the national one, so a code withheld here is served nowhere. The notice says so, since a single geography or a more detailed table can publish fewer.

Two escapes keep the check from costing more than it gives. A dimension published per industry (`ecnbasic` `TAXSTAT` returns only `00` unscoped but `T` and `Y` under `NAICS2017=62`) is left unchecked, because an unscoped check would withhold codes a scoped query does return. A check that fails or comes back empty inside its shorter 20-second budget downgrades to the unchecked map with a notice, rather than emptying the response — the `source` field tells the two apart. Total invocation-budget expiry remains an error; caller cancellation remains `RequestCancelled`. A supplied `geography_level` does not alter or validate this dictionary route: classification and publication checks retain their dataset-wide/national scope, and the response explicitly says so. Live enumeration is separate and validates an explicit level's ability to run without parents.

### Tables that split population groups are named, not probed

On `dec/ddhca` (`T02001`–`T02003`) and `dec/ddhcb` (household type `T03001`–`T03004`, tenure `T04001`–`T04002`), each geography publishes a `POPGROUP` group in only one table of a family, and which one changes between geographies: `1002` (European alone) sits in `T03004` in 5 of Washington's 39 counties, `T03003` in 19, `T03002` in 10, and `T03001` in 5. A query on one table therefore comes back empty for a group a sibling table holds there, a comparison ranks only the geographies its table publishes the group in, a `"*"` breakdown lists only that table's groups, and codes from several tables answer only where the first-listed one publishes the group — a later table reads null there, and the reverse order returns nothing. None of that is visible in the rows.

The families are written down per dataset (`POPGROUP_TABLE_FAMILIES`) rather than read from `variables.json`, which describes each table without saying which groups it serves. A `no_data` hint on such a table names the sibling tables first, ahead of the check-the-value sentence an empty predicated query already carries, since the value is usually valid in a sibling. The same guidance rides the notice of any result that spans several geographies or tables or sets `POPGROUP` to `"*"`, and stays off a single geography's single-table answer for one group, where nothing beside the returned value can be missing. Keying on the table family rather than the dataset is what lets one mechanism cover both files.

Naming the exact table instead was rejected: finding it costs up to three requests per geography, and a failed query would spend them on every caller. The guidance spends none. Merging a group's values across sibling tables is out of scope — the tables measure different category breakdowns, and the two `dec/ddhcb` families' totals (`T03001_001N` households, `T04001_001N` occupied housing units) are separate estimates that differ for most groups.

### Several records per geography are labelled, not collapsed

`pep/charv` publishes an April 1 estimates base and a July 1 estimate for every geography, so a query that pins neither answers with two rows carrying different numbers and, before this, nothing to tell them apart. `MONTH` is what separates them — not `YEAR`, which defaults to 2020 and is carried by both rows, so pinning `YEAR=2020` still returns two. 2021 through 2023 have a July record only, which is why pinning a later year looked like a fix.

The column is recognized from `variables.json` rather than a per-dataset list: a variable the dataset does not mark `required` that carries its own `_LABEL` or `_DESC` attribute is a labelled category the rows vary over. Across every registered dataset and vintage that matches `MONTH` and `UNIVERSE` on `pep/charv` 2023 and nothing else, which lines up with a direct duplicate scan — a `for=state:*` query on every other registered dataset and vintage returns exactly one row per state. `UNIVERSE` takes one value (`R`, Resident Population), so it labels rows without splitting them; the rule tolerates that, since a column that took one value is reported and never named as the cause of a duplicate. The decennial DHC, DP, and S-DHC files, the ACS comparison profiles, supplemental estimates, 1-year subject tables, and selected population profiles were checked when they were registered, at their latest vintage (and 2012 for `acs/acs1/spp`), and add none.

A third label suffix, `_TTL`, labels `POPGROUP` on `acs/acs1/spp` 2012 through 2017. It is read as a label only on a variable the dataset marks `required`: that is the one place it has been seen, and reading it on a non-required variable would make that variable a record dimension, which changes what every query on the dataset requests.

Unlike a required filter dimension, naming one of these in `get=` does not change which rows come back — the API was already returning them all — so requesting them is free of the enumeration flip that rules out echoing `YEAR`. Both the code and its label column are requested, and both are excluded from GEOID composition alongside the requested variables and echoed predicates; a record column left in would concatenate into the GEOID and break every round-trip.

The two data tools answer differently on purpose. `census_query_data` returns every record, labels each row with `record`, renders the record on the row heading so `content[]` carries the same distinction as `structuredContent`, and warns which column separates them and what to pass to pin one. `census_compare_geographies` refuses: a rank is a statement about one geography, so a ranking that lists each one twice with two different values cannot be read correctly however the rows are labelled. It fails with `ambiguous_rows` and names the column and code to pin. Pinning it — `predicates: { "MONTH": "7" }` — is a plain predicate on a variable the dataset declares, so it passes the predicate check and the Census API applies it like any other.

A dataset that declares no filter dimension has no predicate to pick one of those rows by, so the notice and the `ambiguous_rows` recovery name the one column that does separate them. `geoinfo` 2020 publishes a ZCTA, an urban area, a congressional district, or a state legislative district once per delineation — `8600000US98101` is the 2010 ZCTA `acs/acs5` 2020 uses and `860Z200US98101` the 2020 ZCTA of `dec/dhc` and later ACS vintages — so one geography answers on several rows that differ only in `GEO_ID`. `census_query_data` says to add `GEO_ID` to `variables` to label each row and pin one with `predicates: { "GEO_ID": "<its GEO_ID>" }`; `census_compare_geographies` fails `ambiguous_rows` and says to query one geography at a time that way, or compare a vintage with one row per geography. The data tools learn whether the dataset declares any filter dimension from the predicate check, which reports every dimension the dataset declares, set or not; a dataset keeps the filter-dimension wording whenever it declares one.

A predicate set to `*` splits a geography the same way, one row per category of that dimension (1,552 for `cbp` `NAICS2017` in King County), so a wildcarded dimension joins `record` too. The API already echoes its code on every row; the dimension's own `_LABEL`/`_DESC` column adds the label, measured to leave the row count unchanged (1,552 on `cbp` `NAICS2017`, 2,996 on `dec/ddhca` `POPGROUP`) because a measure is always in `get=`. The label comes from that column rather than the `values.item` map because the column exists for `EMPSZES`, `LFO`, and `SEX` as well, while the map covers `NAICS*` and `POPGROUP` only. A dimension with no label column (`pep/charv` `YEAR`) carries its code as its label. The label column is excluded from GEOID composition like the record columns, and the record-row notice and the `ambiguous_rows` hint name the dimension through `record`, quoting at most ten of its values so a thousand-category breakdown does not produce a notice longer than the data. The record-row notice words a wildcarded dimension differently from a record split: the categories are the breakdown the caller asked for, so it says each geography came back on one row per category of that dimension because `predicates` set it to `"*"`, where a `pep/charv` MONTH split tells the caller to pick the record it wants.

### One vintage table, checked before the request

`DATASET_AVAILABLE_YEARS` in `variable-cache-service.ts` is the only place a dataset's vintages are written down. `KNOWN_DATASETS` is its key set, `DATASET_LATEST_YEARS` is the maximum of each list, and `census_list_datasets` reads `available_years` straight out of it. Before, `census-list-datasets.tool.ts` held one copy and the two registries held overlapping others, and none of the three was what a query validated against — which is how `pep/charv` came to advertise three vintages the Census API does not publish.

`VariableCacheService.validateYear` raises `year_not_available` from that table, and both data tools call it before their first request rather than letting the variable cache reach it, because the geography check runs earlier and a vintage the dataset does not serve has no geography metadata either. So a wrong year costs no round trip and reports the year rather than a downstream symptom.

A year is listed only when a query here can answer with it, and that is narrower than what the API hosts for two unrelated reasons: `pep/charv` 2020-2022 are not vintages at all (they are `YEAR` values inside the 2023 vintage), while `cbp` before 2012 and `nonemp` 2008-2011 are real vintages that reject the `NAME` column every query here sends. The error therefore says a year *cannot be queried* rather than that the dataset does not publish it, which would be false for the second kind.

The cost is that a vintage the Census releases is refused until the table is edited. That is the deliberate trade — a wrong year is a common input mistake and a new vintage is a once-a-year event — but it makes the table a maintenance obligation, so it is checked against `api.census.gov/data/<year>.json`, the per-vintage catalog, rather than trimmed by eye.

### A null estimate resolves three ways

Every requested cell used to go through `Number()`, so a cell holding text became `NaN` and serialized to the same `null` as a geography with no value: the text was lost and what was left could not be told apart from missing data. `GEO_ID` is the sharpest case, since it is what a caller reaches for as a join key.

The signal is the value, not the declared type. `variables.json` declares the ACS median-year codes (`B25035_001E`, the `B25037`/`B25039` families) `predicateType: "string"` and serves them ordinary years like `"1983"` that callers rank and average, so keying on the declared type would have stopped returning a number for those; across the registered dataset+year pairs the same mismatch covers dozens of columns (`SUMLEVEL`, `STATE`, `YEAR`, `MONTH`, `NAICS2017`, `EMPSZES` and more) that are numeric in practice. A non-empty cell that does not parse as a number is text; anything else is a number.

Text lands in a new optional `value`, leaving `estimate` null and `suppressed` false, so a null `estimate` now resolves by what sits beside it:

| Cell | `estimate` | `value` | `suppressed` |
|:--|:--|:--|:--|
| A number | the number | absent | `false` |
| Text | `null` | the text | `false` |
| Withheld by the Census | `null` | absent | `true` |
| Empty | `null` | absent | `false` |

The read is per cell rather than per column, which matters in both directions: `GEO_ID` and `pep/charv` `UNIVERSE` are text on every row, while the older ACS profile vintages write "not applicable" as the literal `"(X)"` in a column that is a number everywhere else (`acs/acs5/profile` 2009 answers `DP02_0070E` with `"(X)"`), and that annotation reaches the caller instead of an unexplained null. `format()` renders the text where it used to print `N/A`; a genuinely empty cell still prints `N/A`. On the ranking tool text has no ordering, so sorting on a column of it leaves every row tied — which the `variables` output description says.

Two smaller fixes ride the same read. An empty cell went through `Number("")`, which is `0`, and was reported as a zero estimate; it now reads as missing. And the suppression-code lookup was an unguarded index into an object literal, so a cell reading `"constructor"` would have resolved to a suppression reason — reachable once text flows down this path. The lookup is now keyed by the parsed number (see "ACS sentinel values resolve by number"), so text never reaches it.

### Upstream error bodies are read, not forwarded or stripped

`fetchWithTimeout` attaches the first 500 bytes of a failed response to `data.body` and `data.responseBody`, and those two bodies are not the same kind of thing. A rejected query comes back as one `text/plain` line — `error: unknown variable 'NAME'`, `error: unknown/unsupported geography hierarchy` — which is the entire diagnosis and has no other route to a caller. A path that does not exist comes back as a servlet container's HTML error page, several hundred bytes of styling that says nothing an agent can use.

`censusHttpError` wraps all four `fetchWithTimeout` call sites and reads the body rather than forwarding or dropping it wholesale: a short line with no markup becomes `data.upstreamMessage` and is appended to the error text, and anything else is discarded. `body` and `responseBody` are removed either way, so no markup reaches a caller from any status. The full body stays in the framework's own log line, which is where a maintainer looks for the case the typed errors do not cover.

A 404 on a vintage the table does not list becomes `year_not_available`. A 404 on one it does list does not — the year was validated before the request, so the table has drifted from the API, and answering "no such vintage" while naming that same vintage as available is a loop rather than a recovery. Every other status keeps its status-mapped code, which is what `withRetry` reads, so a 5xx is still retried and a 400 still fails fast; the recovery hint follows the same split rather than telling a caller to retry a query the API rejected outright.

One 400 body gets its own reason. `error: unknown variable '<code>'` naming a code the caller sent becomes `variable_not_found` (NotFound, not retried), with the code in `missingCodes` and a recovery pointing at `census_search_variables` and `census_get_variable`. The data API is the authority on which columns exist: `variables.json` lists annotation and flag columns only inside each entry's `attributes` string, so a pre-check against its keys would refuse all 56,428 `EA`/`MA` columns of `acs/acs5` 2024 and every `_F`, `_LABEL`, and `_DESC` column, all of which the data API accepts. The API names only the first unknown column in a request, which the recovery hint says. Once `withRetry` has given up, `queryData` asks for the sibling dataset that publishes that column and, when one is confirmed, names it in place of the search hint (next section). A rejection naming a column the server added (`NAME`, a label, record, or flag column) stays `upstream_error`, since blaming the caller for it would send them after a code they never passed. The match is anchored on the whole line, so `error: unknown predicate variable: '…'` does not reach it.

### A missing code names the sibling dataset that publishes it

ACS publishes each table family under its own dataset, so a code asked of the wrong one is unknown there: `S1701_C03_001E` is a 404 on `2024/acs/acs5/variables/` and a 200 on `2024/acs/acs5/subject/variables/`. A recovery that sends the caller to search the requested dataset points at the one place the code cannot be. So `variable_not_found` — from `census_get_variable` and from both data tools — names the sibling that holds the code, confirmed rather than guessed: `VariableCacheService.findSiblingDatasets` asks each candidate's per-variable endpoint for the code (`/data/<year>/<sibling>/variables/<code>.json`, 200 holds, 404 does not). The prefix alone does not settle it — `S0201_001E` is in `acs/acs1/spp`, not the subject tables, and `DP1_0001C` in `dec/dp`.

| Prefix (then a digit) | Candidates |
|:--|:--|
| `B`, `C` | `acs/acs5`, `acs/acs1` |
| `S` | `acs/acs5/subject`, `acs/acs1/subject`, `acs/acs1/spp` |
| `DP` | `acs/acs5/profile`, `acs/acs1/profile`, `dec/dp` |
| `CP` | `acs/acs5/cprofile`, `acs/acs1/cprofile` |
| `K` | `acs/acsse` |

The requested dataset and any candidate not listed for the year are left out, and the requested survey's own datasets go first (`acs/acs1/spp` ahead of `acs/acs5/subject` for a code missing from `acs/acs1/subject`). Decennial `P`/`H` tables sit in several `dec/*` datasets at once and business and estimate codes carry no table prefix, so they have no row and keep the search hint.

Decisions:
- **Only on the failure path.** A successful call sends exactly the requests it did before; the probes cost a failed call 0.30–0.77 s each.
- **One chain per table, at most five tables, one 2.5 s deadline for the whole error.** The first missing code of each table is probed, candidates in order; tables run in parallel. The deadline covers a three-candidate chain at the slowest measured lookup and is shortened to the invocation time remaining on keyed calls. Expiry preserves the established `variable_not_found` and its search hint.
- **Outside `withRetry`.** A probe is expected to 404, so it must not spend the retry budget; the data path runs it once, after its retries are over.
- **Best effort, except cancellation.** A probe that fails or runs out of time ends its chain and leaves that code with the search hint. A caller's cancellation is rethrown, never answered with a partial hint.
- **Per-variable probe, not the sibling's `variables.json`.** Loading `acs/acs5/subject` 2024's would cost 7.9 MB and 11 s on an error path.
- **The query is not rerouted.** The caller asked for one dataset; the hint names the other and leaves the choice to them.

`census_search_variables` uses the same lookup when a code-shaped query matches nothing whole — a variable code through `variables/<code>.json`, a table ID through `groups/<id>.json` (`groups/S1701.json`: 200 on `acs/acs5/subject` 2024, 404 on `acs/acs5`) — and names the sibling in the empty-result notice. `census_query_data` asks the same of `groups/<id>.json` when its `group` table is unknown to the dataset (see "A table comes back whole through `group`"). A keyword query, matched or not, and a code that matched, send only `variables.json`; see "Variable search is client-side, not a Census API feature".

### Codes are sent in the dataset's spelling

The Census API matches `get=` case-sensitively. Every registered dataset names its columns in uppercase except the comparison profiles' statistical-significance columns, `CP03_2024to2019_062SS` (696 on `acs/acs5/cprofile` 2024, 2,784 on `acs/acs1/cprofile` 2024), which upstream rejects uppercased; no two columns collide once uppercased. Both data tools uppercase and dedupe the caller's codes, check `sort_by` against them before any request, then map each through `VariableCacheService.resolveSpellings` — the resolver `census_get_variable` uses — to the spelling the dataset publishes. That spelling goes into `get=` and keys each row. The predicate check has already loaded `variables.json` by then, so the mapping spends no request. A code the dataset does not list is sent uppercased, so its rejection is `variable_not_found` naming that form.

### ACS sentinel values resolve by number

The ACS writes a value it cannot publish as a negative sentinel, and the Census [estimate and annotation values table](https://www.census.gov/data/developers/data-sets/acs-1year/notes-on-acs-estimate-and-annotation-values.html) says what each means. The table covers the 1-year and 5-year surveys alike, and no vintage checked assigns a code a different meaning. The lookup is keyed by the parsed number, not the string: subject and profile percent columns write the same sentinels as floats (`-666666666.0`), and a string key resolved the integer form while leaving the float form in the same row suppressed with no reason.

Two sentinels are not withholdings. `-555555555` marks the margin of error of an estimate controlled to an independent count, which the Census says "may be treated as zero", and the 2009 vintage writes the same cell as a literal `0`, so it reads as the number zero and the estimate it pairs with carries `moe: 0`. `-333333333` marks a margin of error that cannot be computed because the median falls in the lowest or highest interval of an open-ended distribution. The estimate beside it is that interval's boundary (`250001` for "250,000+", `9999` for "10,000-"). The figure is kept and flagged `open_ended` rather than suppressed: as a bound on the true median it still ranks correctly against ordinary values, and geographies sharing it tie. The flag names neither end, because the MOE code is the same for top and bottom coding. Direction lives only in the `EA` annotation (`250,000+` vs `10,000-`), which a caller may not have requested. The flag needs the `M` code in the same request, since that sentinel is the only signal.

The meanings, the zero MOE, and `open_ended` apply to ACS datasets only, through the same `isAcsDataset` gate the E/M pairing uses. The other families withhold through flag columns instead, so a value below −100,000,000 there stays suppressed with no reason rather than borrowing ACS's meaning.

| Value | Meaning |
|:--|:--|
| `-666666666` | Estimate not computable: too few sample observations (also a ratio of medians with a median in an open-ended interval, and a 5-year median whose margin of error exceeds it) |
| `-999999999` | Cannot be displayed: too few sample cases in the geography |
| `-888888888` | Not applicable or not available |
| `-222222222` | Margin of error not computable: too few sample observations |
| `-333333333` | Margin of error not computable: the median falls in an open-ended interval — the estimate is flagged `open_ended` |
| `-555555555` | Controlled estimate — the margin of error reads as `0`, not a suppression |

### Business-dataset flags are read, not trusted as zeros

`cbp`, `ecnbasic`, and `nonemp` publish a flag column beside each measure (`RCPTOT_F`, `EMP_F`, `NESTAB_F`). A value the Census withholds is written as `0` in the measure with a symbol in the flag — the CBP record layouts say "Employment or payroll field set to zero" — so without the flag a withheld value reads as a real zero: four hospitals with 2,955 employees in Chelan County, WA reported zero receipts. Each requested measure that publishes a flag column gets it added to `get=`, and a withholding symbol replaces the number with `suppressed: true` and the symbol's meaning. Every flagged cell also carries `flag: { code, meaning }`.

The symbols and meanings come from the 2022 Economic Census data dictionary, the CBP record layouts and methodology, and the Nonemployer Statistics methodology. A live survey of `cbp` 2012/2016/2017/2019/2023, `ecnbasic` 2012/2017/2022, and `nonemp` 1997/2002/2005/2007/2012/2016/2023 found every withholding symbol alongside a `0`:

| Symbols | Meaning | Value |
|:--|:--|:--|
| `D` | Withheld to avoid disclosing data for individual companies | withheld |
| `S` | Withheld because the estimate did not meet publication standards (CBP uses it in place of `D` from 2017) | withheld |
| `N`, `Q`, `X`, `*` | Not available or not comparable; revenue not collected at this level for multiestablishment firms; not applicable; sampling variability not shown | withheld |
| `a`–`m` | Withheld, with the published employment range (`j` = 10,000 to 24,999 employees) | withheld |
| `B`, `I`, `K`, `L`, `M`, `O`, `R`, `T`, `U`, `W` | Withheld, with the published sales range | withheld |
| `0`–`9`, `G`, `H`, `J`, `^` | Data quality band (imputation rate or relative standard error); noise infusion level | a range in place of a number beside `0`; kept beside a nonzero figure |
| `r`, `s`, `A`, `Z`, `-` | Revised; relative standard error above 40% or at least 100%; rounds to zero | kept |

The symbols are case-sensitive — `j` is an employment range and `J` is high noise — and the annotating ones keep the figure, since the survey found `s` beside a published count (`ecnbasic` 2012, Washington, `ESTAB` 53). The band symbols are what the range columns publish: those columns hold `0` in the measure and the range in the flag — `cbp` `EMP_N` ("Noise range for number of employees") and its payroll siblings carry `G`/`H`/`J`, and `ecnbasic` `RCPTOT_IMP` ("Range indicating imputed percentage …") and its siblings a digit. A survey of every flagged `ecnbasic` measure for Washington in 2012, 2017, and 2022, and of the `cbp` and `nonemp` range columns, found the band symbols only beside a `0`. That zero reads as `suppressed: true` with the band ("Published as a range rather than a number: …"); read as `0`, it put every county at a tied `0` in a ranking. Beside a nonzero figure the same symbol can only annotate it, so the figure is kept. A symbol the documentation does not define is treated as withholding, because trusting its zero is the failure the flags exist to prevent.

The flag column is found from `variables.json`, not a dataset list. Current vintages name it in the measure's `attributes`, and the older `nonemp` vintages publish it as a variable of its own. Only numeric measures qualify: the same suffix flags a dimension (`NAICS2017_F`) and footnotes a text column (`GEO_ID_F`, "Geo Footnote"), and neither withholds a value. Flag columns are extras under the column limit below — when they do not fit, the request still goes out and the notice names the codes whose flags went unchecked.

### A table comes back whole through `group`

A table past 49 codes with its margins cannot be asked of `variables`: 291 of the 1,199 `acs/acs5` 2024 tables are, and sex by age (`B01001`, 49 lines) would take two calls joined by GEOID. The Census API's `get=group(<ID>)` returns a whole table in one request, and the 50-column limit does not count it, so `census_query_data` takes a `group` input: one table ID, beside or in place of `variables`. Splitting `variables` across several upstream requests and merging by GEOID would also lift the cap, at one request per 49 codes and a join on every page.

- **Resolution.** The ID is matched regardless of case against the table IDs in the cached `variables.json` (`VariableCacheService.resolveGroup`) and sent in the dataset's spelling, which the API matches exactly. A `variables` entry written `group(<ID>)` reads as `group`; sent as typed it would go upstream as `GROUP(…)` and surface as `no_data`. Two different tables are `multiple_groups`, and neither input is `variables_or_group_required`.
- **Unknown table.** `variable_not_found` before any data request, with the sibling-dataset hint of the next section probed through `groups/<ID>.json`.
- **Rows.** Each row keys the caller's `variables` first, then the table's columns in line order — computed from `variables.json`, each column followed by its attributes — decoded and estimate/margin paired as for `variables`. Annotation columns (a code plus `A`) are left out, since the decoded value already carries the meaning the annotation gives. The comparison profiles' `SS` columns stay. The table's `GEO_ID` and `NAME` join only when `variables` lists them, and the table's columns never enter the GEOID. `variable_labels` is built from the same list, so it labels every column of the table.
- **Column limit.** The `group(<ID>)` item is not counted, and a listed code the table returns is sent once (`codesSentFor`), so `variables` keeps its own 49-code limit.
- **Excluded datasets.** `cbp`, `ecnbasic`, `nonemp`, `pep/charv`, `dec/ddhca`, `dec/ddhcb`, and `acs/acs1/spp` are `group_not_supported` before any request: their tables carry filter or record dimensions, which turn the API's default into one row per category.
- **Cost.** Every matched row is fetched before paging, so a wide table over a broad `"*"` scope can outrun the 15-second attempt ceiling (`group(DP05)` for every county is 16.4 MB and took 26.5 s). The deadline error names a narrower geography, or listing only the needed codes in `variables`. `census_compare_geographies` takes no `group`, since it ranks on one column.

### The 50-column limit counts every column sent

The Census API rejects a `get=` list longer than 50 columns (`NAME` plus 49 codes succeeds, plus 50 fails with `error: 'get' is limited to 50 variables`), and every query here sends `NAME`. The limit is checked against the columns actually sent, built by the same function `queryData` uses, before the data request. Two kinds of added column count as fixed: the label column for each filter dimension left unset, and both columns of each record dimension. Past the limit, `too_many_variables` states the most the query can carry and names the added columns. That is 49 codes on ACS, 46 on `cbp` 2023 with its three dimensions unset, and 41 on `pep/charv` 2023, which adds eight columns. Both data tools enforce the limit. A table requested through `census_query_data`'s `group` is one `group(<ID>)` item that the plan does not count, and a listed code it returns is dropped from the named columns, so neither takes a slot.

Wildcard label columns and flag columns are extras. They take whatever room is left, label columns first, and whatever does not fit is left off the request and named in the notice rather than failing the call. Adding either never turns a query that fit into one the API rejects. A missing label column costs only the label, since the row keeps the category code. A missing flag column is the serious case, because a withheld value then reads as `0`, and the notice says so for each code.

Every column goes out once. A caller can name a column the server adds anyway — `MONTH_DESC` on `pep/charv`, a flag column such as `EMP_F`, a dimension's `_LABEL` column — and the request sends it and the plan counts it a single time, so naming it neither wastes a slot nor lowers the maximum the refusal states. Repeated and blank variable codes are dropped before the plan is made.

### Variable search is client-side, not a Census API feature

The Census API does not provide a variable search endpoint. `census_search_variables` fetches and caches the full `variables.json` for the requested dataset+year, then does keyword matching in-process against `label` and `concept` fields. The cache TTL (default 24h) means the first request per dataset+year is slow (several MB JSON download), but subsequent searches are instant. This is the only viable approach given the API's design.

The rule uses sort keys only, no weights:

- **Codes.** An agent holding a code (`B19013_001E`, `B19013`, `NAICS2017`) reaches for search first, and labels and concepts never hold codes. When the query, trimmed of surrounding spaces, quotes, or punctuation, is one token equal to a variable code or single-table `group` in the dataset's spelling, those variables form a tier above keyword matches, in code order: `B19013` returns `B19013_001E` then `B19013_001M`, and `P1` on `dec/pl` starts at `P1_001N`. `totalMatches` counts both tiers, a variable is listed once, and offset/limit slice the combined list. Shared columns such as `GEO_ID` belong to no single table and stay out of that tier. Once a code matched, a most-words keyword fallback is dropped and no partial-match notice is given. A page ending inside the code tier names its last code and `nextOffset`: adding words to a table code prevents code matching, while continuation reaches the remaining table unchanged.
- **Code guard.** Letter-only words are column codes on some datasets (`AGE`, `SEX` on `pep/charv`, `STATE` on `acs/acs5`) and ordinary keywords everywhere. A token without a digit or underscore takes the code tier when the keyword search matched nothing, so `POPGROUP` and `popgroup` on `acs/acs1/spp` find their column. When keywords did match, it leads them only if typed exactly as the dataset spells the code — uppercase — and those matches leave a variable of it out: `STATE` on `dec/dhc` 2020 puts the column (labelled "Geography") ahead of the six group-quarters rows holding "state", while `state` and `State` return those six alone; `BENEFIT` on `ecnbasic` ("Total fringe benefits") leads `BENPEB`, the one label holding the word "benefit", which `benefit` returns alone; and `age` or `AGE` keeps its keyword order on `pep/charv` (`MEDAGE`, `AGE`, `HISP`, `POPGROUP`), which already holds AGE. Case is the signal because a caller holding a code copies it as published, while a caller typing a word rarely capitalizes all of it. A token with a digit must equal a code or table exactly, so `2020` (110 keyword matches on `acs/acs5` 2024) is unchanged. No grammar covers every dataset's codes (`CB2300CBP`, `PEP_ALLDATA`, `PCT12E`, `CP03_2024to2019_106SS`), which is why the match is against the dataset's own codes rather than a pattern.
- **Empty code-shaped result.** A token shaped like a code — a letter, then letters, digits, and underscores, with a digit or underscore among them — that matches no code and no variable whole — nothing at all, or only some of its words, as `CP03_2024_062E` does on `acs/acs5`, where "2024" is a word of every income label — is checked against the dataset's attribute columns (no request), then asked of the sibling datasets as under "A missing code names the sibling dataset that publishes it". An attribute column or a confirmed sibling replaces the most-words results, which hold only fragments of the code; with neither, those results stay, and a query that had none gets the notice that the dataset has no such code. A lookup that fails or times out counts as no sibling; the caller's cancellation is rethrown. A plain word, a number, or a hyphenated word that matches nothing (`xyzzy`, `65`, `covid-19`) sends no lookup and keeps the keyword advice.
- **Match.** A query word matches a whole word of the label or concept, both split on every run of characters that is not a letter or digit and compared case-insensitively. The earlier substring match let `rate` match "separated".
- **Shared columns.** A column whose `group` names more than one table is matched on its label only and returned without a concept. Its concept joins every table's (99,266 bytes for `GEO_ID` on `acs/acs5` 2024), so it matched almost any query and made up most of any payload it appeared in. There is no length threshold: the join is what makes the concept meaningless, whatever its size.
- **Margins of error.** An ACS margin of error is matched on its estimate's label, not its own. Its own opens with `Margin of Error!!`, and those words would rank it alone above its estimate for any query holding "of". Matched this way, the two tie, and the code puts the estimate first.
- **Filter.** A keyword result contains every distinct query word, and `totalMatches` counts only those, plus the code tier. When no variable contains every word, the results are the variables containing the most, and the notice says how many of how many. The earlier any-word scoring counted 19,423 matches for "median household income" and ranked `B19013_001E` 24th.
- **Order.** Below the code tier, where the query appears, best first: the label's last `!!` segment or the whole concept equals it; the phrase is in both label and concept; in the label only; in the concept only; the words are present but not as a phrase. Ties go to fewer `!!` segments in the label, then a shorter concept, then the code. Depth is what puts a table total (`S1701_C03_001E`) ahead of its breakdown rows, concept length what puts a base table (`B19013`) ahead of its race-iteration variants, and the code what puts an `E` estimate ahead of its tied `M` margin of error.

A partial match inherits the same order, which can surface an unexpected word: no `acs/acs5` variable holds both "poverty" and "rate", so "poverty rate" returns the one-word matches led by the `B98` coverage-rate tables, with the notice saying it matched 1 of 2 words. The published poverty rate lives in `acs/acs5/subject` (`S1701_C03_001E`).

## Workflow Analysis

### Primary workflow: "What's the median household income in King County, WA?"

| # | Call | Tool | Purpose |
|:--|:-----|:-----|:--------|
| 1 | Search for variable | `census_search_variables` | Query "median household income", identify `B19013_001E` |
| 2 | Resolve geography | `census_resolve_geography` | "King County, WA" → state_fips: `53`, county_fips: `033` |
| 3 | Query data | `census_query_data` | geography_level: `county`, geography_fips: `033`, parent_fips: `53` |

Three calls total. If the agent already knows the variable code, steps 1–2 collapse to one. If the agent already has FIPS, step 2 is skipped entirely.

### Secondary workflow: "Compare poverty rates across all states"

| # | Call | Tool | Purpose |
|:--|:-----|:-----|:--------|
| 1 | Confirm variable | `census_get_variable` | `S1701_C03_001E` on `acs/acs5/subject` — "Percent below poverty level", the total row of that column (the `census_compare_geographies` description names it) |
| 2 | Compare | `census_compare_geographies` | dataset: `acs/acs5/subject`, variables: `["S1701_C03_001E", "S1701_C03_001M"]`, geography_level: `state`, no `within` (all states) |

Two calls. `census_compare_geographies` handles the wildcard state query and sorting internally. Ranking the headcount `B17001_002E` instead would rank states by size, not by rate. Searching "percent below poverty level" on `acs/acs5/subject` matches every breakdown row of the column (9,758 variables in 2024), and the total row `S1701_C03_001E` ranks well down that list, so the step names the code rather than searching for it.

### Discovery workflow: "What ACS data exists for ZIP codes?"

| # | Call | Tool | Purpose |
|:--|:-----|:-----|:--------|
| 1 | List geographies | `census_list_geographies` | Check if ZIP code tabulation areas are a supported level for `acs/acs5` |
| 2 | List datasets | `census_list_datasets` | Find which dataset/year combinations cover ZCTAs |
| 3 | Search variables | `census_search_variables` | Find relevant variables for the ZCTA dataset |

Note: ACS5 supports ZCTAs (`zip code tabulation area`), but the geography name in the API is not "zip code" — `census_list_geographies` surfaces the correct term, and `census_resolve_geography` turns a ZIP into its ZCTA code.

## API Reference

### Query structure

```
GET https://api.census.gov/data/{year}/{dataset}?get={vars}&for={geo}&in={parent_geo}&key={key}
```

- `{year}`: e.g., `2024`
- `{dataset}`: e.g., `acs/acs5`, `acs/acs1`, `acs/acs5/profile`, `acs/acs5/subject`
- `{vars}`: comma-separated column names, at most 50 per request counting `NAME` and every attribute column, always include `NAME`; matched case-sensitively (every supported dataset names its columns in uppercase, except the ACS comparison profiles' significance columns such as `CP03_2024to2019_062SS`, which the API rejects uppercased — so the data tools send each code in the dataset's spelling; see "Codes are sent in the dataset's spelling")
- `for={level}:{code}`: e.g., `county:033`, `county:*` (wildcard), `state:*`
- `in={level}:{code}`: parent geography filter, e.g., `in=state:53`
- `key={key}`: required for all data queries

### Response format

JSON array, first row = column headers, subsequent rows = data:
```json
[
  ["NAME", "B19013_001E", "state", "county"],
  ["King County, Washington", "98144", "53", "033"]
]
```

Values are strings. On ACS, negative values (-666666666, -222222222, etc., also written as floats like -666666666.0 in percent columns) are Census annotation sentinels, not real data. On the business datasets a withheld value is `0` with a symbol in the measure's `_F` column.

### Variable code anatomy

`B19013_001E`:
- `B` prefix: Base table (detailed). `C` = collapsed. `DP` = data profile. `S` = subject table.
- `19013`: Table number (household income)
- `_001`: Cell/line within the table
- `E`: Estimate. `M` = margin of error. `EA` = estimate annotation. `MA` = MOE annotation.

### Geography hierarchy and FIPS

Census geographies nest: us → region → division → state → county → tract → block group. Lower levels require parent FIPS in the `in=` parameter. County FIPS are 3-digit (zero-padded), state FIPS are 2-digit, tracts are 6-digit (`dec/pl` 2000 lists a whole-number tract by 4).

TIGERweb endpoint for county lookup:
```
GET https://tigerweb.geo.census.gov/arcgis/rest/services/TIGERweb/State_County/MapServer/1/query
  ?where=NAME LIKE '%King%'&outFields=NAME,STATE,COUNTY&f=json
```

### Suppression codes

The ACS sentinel meanings and the business-dataset flag symbols are tabled under "ACS sentinel values resolve by number" and "Business-dataset flags are read, not trusted as zeros" above.

## Known Limitations

- **API key required, no free tier.** As of 2025, the Census API enforces key authentication on all data queries. The key signup is free but required.
- **Variable search is approximate.** With 28K+ variables, keyword search returns many results. Agents should confirm codes via `census_get_variable` before relying on them in queries.
- **ACS publication coverage varies by product.** One-year, supplemental, comparison-profile, and selected-population products have different area/subgroup rules, with continuity and metropolitan-area exceptions. Empty results and unmatched-member notices describe the applicable rule as a possible cause, preserve code/predicate guidance, and suggest broader coverage with variable rediscovery; they do not infer population from absence. See "ACS publication coverage guidance".
- **Margin of error is not a guarantee.** ACS data is survey-based. MOE values can be larger than the estimate for small geographies or rare populations. The server returns MOE columns alongside estimates but doesn't validate statistical reliability.
- **49 variables per request, fewer on some datasets.** The Census API caps `get=` at 50 columns, and `NAME` plus any added label and record columns count toward it — 49 codes on ACS, 46 on `cbp` 2023 with its filter dimensions unset, 41 on `pep/charv` 2023. Both data tools refuse a longer request with `too_many_variables`, naming the exact maximum. One whole table needs no splitting: `census_query_data`'s `group` returns every column of it outside that limit, on the datasets without filter or record dimensions. Codes drawn from several tables still take multiple calls.
- **No historical ACS1 for 2020.** ACS1 2020 was not released due to COVID-19 data collection disruptions. A 2020 ACS1 query fails with `year_not_available` before any request.
- **Margins of error exist only on ACS.** `pep`, `dec`, `cbp`, `ecnbasic`, `nonemp`, and `geoinfo` publish none, so `moe_code`/`estimate_code` are absent there and query rows carry no `moe`. A code ending in `E` in those datasets is an ordinary code, not an estimate with an `M` sibling.
- **Some business-dataset geography levels have no name-to-code path.** State, county, CBSA, CSA, consolidated city, and `ecnbasic` 2022's economic place all resolve from a name. `cbp`'s congressional district and ZIP code, and `ecnbasic`'s region and metropolitan division, do not, and none needs a resolver: a congressional district is its zero-padded district number under a state parent (`00` at large, `98` for the DC delegate), a ZIP code is the ZIP itself, and a region is one of four fixed codes (`1`–`4`, published by `ecnbasic` for the Construction sector only). `metropolitan division` is left out deliberately: its parent is the CBSA level, and `census_query_data` can express only `state`, `county`, and `tract` in its `in=` clause, so a resolved code would land on `parent_required` with no input able to satisfy it.
- **Business-dataset vintages predate the query shape.** Every query sends `NAME` in `get=`, and the older vintages reject it with a `400` — `cbp` before 2012, and `nonemp` 2008 through 2011. Those years exist upstream but are omitted from `census_list_datasets` rather than advertised and then failing. `cbp` vintages before 2017 also take `NAICS2012` rather than `NAICS2017`, and `nonemp` runs back through `NAICS1997`; the predicate check reads each vintage's own `variables.json`, so the right code name is reported at runtime.
